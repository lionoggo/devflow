## 1. 结论

第 2 阶段做四件事：

## 2. 四项新增的决定

### 2.1 影响面分析

**作用**：在改动落地前回答"这次改动还会弄坏哪里"。做法不是列一串可能，而是找出"它之所以安全，靠的是哪一个事实"，并跑代码证明这个事实。它针对的是"只修个例、其他地方坏了"和"说完成其实没验证"这两类问题。历史统计只能说明这两类纠正最多（207、135 次），不能证明它们主要由缺少影响面分析导致；效果在试用期（E1）观察。

**pstack 原版**有 6 步、5 级证据，大改动还会让多个模型并行分析。为了简单易用，dflow 压缩为一份共用说明 `references/impact.md`，不单独建剧本：

- **三步**：
  1. 说清改动实际做了什么，包括 diff 没写出来的行为变化。
  2. 查 grep 看不到的地方：
     - 数据格式和存档；
     - 配置和开关；
     - 另一种语言或另一个进程读同一份数据；
     - 运行时序，例如异步和销毁顺序；
     - 三层以外的下游。
  3. 找出安全依赖的那一个事实（例如"这个函数只在启动时调用一次"），写一个最小脚本或测试，调用真实代码去证明。证明不了就写"未证明"。
- **证据三级**（替代原版五级）：推测、指到代码行、跑过证明。每条结论都标出到了哪一级。
- **输出**：
  - 一句话结论：安全、有风险，或未证明；
  - 安全依据及其证据等级；
  - 风险最多 5 条，每条写位置、怎么坏、可能性、代价、怎么查；
  - 已排除的项目；
  - 合并前最便宜的一个检查。
- **三处使用**：
  1. **显式询问**：用户说"影响面""会影响什么""这个改动安全吗"，按上面三步完整做。
  2. **实施提交前自动做**：
     - 触发条件按 diff 判定，命中任一即触发：
       - 改了被其他文件引用的函数、类或接口的签名或返回值；
       - 改了数据或存档格式、配置键；
       - 删除了代码；
       - 一次提交跨两个以上顶层目录。
     - 触发后完整走一遍三步，至少运行一个能区分好坏的检查；跑不了就标"未证明"。
     - 收尾报告固定写一行：`影响面：<安全依据>（<证据等级>）；检查：<命令和结果>`。
     - 这一步替代 `playbooks/build.md` 里现有的"列调用方、数据读取方和配置"一句，不重复。
  3. **代码评审**：评审剧本评审代码时，按同一份说明检查。
- **不做**：原版"大改动多模型并行"不做。需要独立复核时，按 SKILL.md 的跨模型规则执行。

### 2.2 去 AI 腔

**作用**：让文档、周报、交接提示词、提交信息读起来像人写的。它针对的是"看不懂、太长、自造术语"这一类纠正（约 78 次）。

**pstack 原版**是英文清单（33 条，含破折号、冒号、AI 词汇），直接照搬对中文无效。所以重写为中文清单 `references/unslop.md`，分六组：

| 组 | 代表模式 | 改法 |
|---|---|---|
| 空话 | "值得注意的是""总的来说""在…的背景下""希望对你有帮助""好问题" | 删 |
| 堆词 | 赋能、抓手、闭环、打通、沉淀、心智、底层逻辑、范式 | 换成具体动作或对象 |
| 句式 | "不仅…而且…"、凑够三项的排比、"从 X 到 Y"的假范围、同一对象换多个说法 | 直接说；按真实数量列；同一对象只用一个词 |
| 翻译腔 | "对…进行了…的操作""被…所""作为一个…" | 主动句，动词直说 |
| 排版 | 每行粗体标签加冒号、加粗泛滥、装饰 emoji、破折号串句、箭头和缩写代替句子 | 改成完整句；粗体只留真正的关键词 |
| 内容 | 自造术语、内部编号、英文字段名；只描述感受，不给机制或数字；模糊归因（"业内普遍认为"） | 写清机制或数字；说出来源，否则删 |

英文文本（提交信息、代码注释、英文文档）沿用原版中适用的条目：AI 词汇、空话、被动语态、过度压缩。

**配套检查** `scripts/slop-check.sh <文件…>`：
- 用固定词表 grep，输出命中的行号和词。退出码：0 表示无命中，1 表示有命中，2 表示参数错误。
- 跳过代码块和引用块。
- 行尾写 `<!-- slop-ok: 理由 -->` 可以豁免该行，用于"链路"在网络语境这类正当用法。
- 只报告，不自动改，也不阻断任何操作。
- 配一份正例和反例语料，`scripts/slop-check-test.sh` 用它们做测试。

为什么现在就做脚本：用户历史里同类纠正已经反复出现，满足"结构化教训"原则"出现两次就结构化"的条件。词表能查的那部分交给脚本，句式问题仍按清单人工改。

**何时用**：
- 用户说"润色""去 AI 腔""精简这段"，按清单改写。如果是文件，就直接改文件并本地提交。
- 写方案文档、周报、交接提示词、PR 正文这类会被他人或日后阅读的文本时，写完先对文件跑一次 `slop-check.sh`。每个未豁免的命中，要么改掉，要么写出保留理由。
- 普通对话回复不逐条过清单，只把空话、堆词、自造术语三组并入 SKILL.md 的回复规则。

### 2.3 原型

**作用**：一个分歧能靠"看一眼"判断时，用一次性原型的结果来决定，而不是来回讨论，或者直接改生产代码去试。"不停下等人"原则已经要求能用实验回答的就不问人，但没说怎么试，原型剧本补上这一步。

对用户的价值是推测，在试用期观察。依据是：
- ludus 和 Studio 以游戏和界面为主，"哪种布局、哪种展示方式"这类问题常见；
- 不认可和过度设计两类纠正里，可能有一部分本可用并排比较的结果结束争论。

**代价**：几分钟时间，加上临时目录里的文件。**风险**：原型代码混进生产代码。所以规则是：原型只放临时目录，从不提交；用户选定后，转实施剧本按正常标准重做。

**本阶段只做界面原型**（`playbooks/prototype.md`），共五步：
1. 写下原型要回答的那一个问题。没有问题就不做原型，转实施。
2. 在临时目录里写一个 HTML 文件，用按钮切换两到三个变体，每个变体有标签。不用框架和构建工具，可以用 CDN。不写测试，不做抽象。
3. 用浏览器打开（必要时起一个临时静态服务器，端口被占用就换一个），截图每个变体。
4. 给出各变体的截图、取舍和推荐。审美偏好仍由用户决定，截图只是比较材料。
5. 关掉启动的服务器进程，写明"原型是一次性的"以及路径。用户选定后转实施。

没有浏览器或截图工具时，如实说明，只交付 HTML 文件和推荐，不冒充"已看过"。

行为和时序类分歧（哪种做法更快、哪种输出对）不并入原型剧本，继续按"不停下等人"原则做最小实验。等真实使用中反复出现，再决定是否并入。

**何时用**：
- 用户说"做个原型""哪种效果好""先做出来看看"，路由到原型。
- 方案剧本比较方向时，如果遇到界面上的分歧，调用原型。

### 2.4 多方案并行（arena）：不单独加入

**它做什么**：同一个任务派 N 个子 agent 各做一版，再派一个评判，选一版为底，从落选版本里移植一两处优点。

**加入后的作用和代价**：
- **作用**：避免第一版就把方向定错，适合重要、一次做错代价大的产物，例如核心接口设计。
- **代价**：按调用次数估计，至少是单次的 3 倍（2 个候选加 1 个评判），没有 token 或时长的实测。另外还需要隔离的输出目录。这与用户"默认精简"的决定冲突。
- **已有替代**：
  - 跨模型视角：方案定稿前的 codex 评审已经提供；
  - 界面分歧：原型（2.3）能直接并排比较；
  - "对比两个方案"：评审剧本已覆盖。

**决定**：不建 arena 剧本，只把它的取舍做法写进方案剧本的方向比较：
1. 先列出决定性的约束，被硬约束淘汰的方向直接排除；
2. 剩下的方向用一张逐项取舍表比较，不打分，不凭整体印象；
3. 选一个方向为底，从落选方向里最多移植一两处优点，并注明来源。

用户明确要求"并行出几版"时，才按 arena 的方式做两个候选，一个由 Claude 子 agent 做，一个由 codex 做，开始前先说明成本。这一条写在方案剧本里，不单独成剧本。

## 3. 第 2 阶段的 7 个剧本

每个剧本先照搬或改写来源，再按用户规则调整授权和语言。篇幅以一屏能读完为准。

| 剧本 | 文件 | 来源 |
|---|---|---|
| 评审 | `playbooks/review.md` | `pstack:interrogate` 的四档判断；`references/plan-review.md` |
| 调研 | `playbooks/research.md` | devflow-research（含图表、行业对比、报告模板）；`pstack:how`、`pstack:why`；已有的 `references/epistemics.md` |
| 交接 | `playbooks/handoff.md` | devflow-impl `references/handoff.md` |
| 进展 | `playbooks/status.md` | `pstack:ketchup` |
| 周报 | 独立技能 `skills/dflow-report/`；`playbooks/report.md` 只写一行，指向它 | devflow-report 原样迁移，含 `agents/openai.yaml` |
| 提交与发布 | `playbooks/ship.md` | devflow-commit 的安全规则；`pstack:poteto-mode/playbooks/opening-a-pr.md` 的 PR 正文模板；`babysit.md` 的跟进规则 |
| 调优 | `playbooks/tune.md` | `pstack:correct`；`pstack:reflect` 的筛选标准；`pstack:poteto-mode/playbooks/authoring-a-skill.md` |

各剧本要点：

**评审**
- 先用一段话写清评审对象的意图。
- 调用评审剧本本身就视为用户要求独立评审，所以默认用 `codex exec -s read-only` 做。评审方只拿到评审对象和证据，不看作者的结论。SKILL.md 的跨模型规则同步加上这一处（见第 6 节）。
- 结论分四档：
  - 必须改：不超过 5 条；
  - 值得考虑；
  - 知道即可；
  - 不采纳：附理由。
- 第一行写评审模型和输出文件路径。codex 不可用时写"未审查：<原因>"，主模型给出的意见标为"主会话意见"，不说成独立评审。
- 代码评审时按 `references/impact.md` 检查影响面。
- 不自动修改。

**调研**
- 先区分"代码怎么工作"和"为什么这样设计"。
- 设计意图没有书面依据时，标为推测。
- 需要外部资料时，用 `references/prior-art-research.md`。
- 结论放第一段。

**交接**
- 写出给新会话或其他 agent 的提示词，包含：目标、完成条件、当前状态（分支、HEAD、已做和未做）、已知死路、证据位置。
- 按去 AI 腔清单写。
- 提示词先给用户看，用户说"派发"才派发，因为派发是对外动作。

**进展**
- 只读。从对话、`git log`、todo 和日志收集信息。
- 开头一句话说"有 N 件事需要你"，或"没有"。
- 每件事写结果和状态：完成、进行中、失败、未验证。
- 需要用户决定的事各写两行：一行写推荐和理由，一行写不回复会怎样。
- 全文 150 字左右。不画图，用户要求才画。

**周报**
- 单独成技能，是因为 Codex 要能直接调用。现有 devflow-report 只安装在 `~/.codex/skills`（`install.sh` 第 10–15 行）。
- dflow-report 同时安装到 `~/.codex/skills` 和 `~/.claude/skills`。
- 内容不变，只改名，输出规则里加上去 AI 腔清单。

**提交与发布**
- 本地提交直接做，按功能拆分。
- 已暂存的改动沿用 devflow-commit 的范围判断：
  - 属于本次范围的，单独提交；
  - 明确无关的，保持不动；
  - 无法判断的，列出文件和摘要后问用户。
  - 任何情况下都不 reset、不 unstage、不混入其他改动。
- 钩子失败就停下报告；不用 `--no-verify`。
- push、开 PR、回复评论、合并，都先问用户。
- PR 正文用中文模板，依次写：为什么、改了什么、范围、影响面、验证。
- 跟进 PR 时，每次操作前重新读取状态和评论，不复用旧结果。修复在本地提交，推送前再问。

**调优**
- 一类错误出现两次才算。
- 按"结构 → 类型或检查脚本 → 行为测试 → 文字规则"的顺序，选最高的可行层级。
- 新检查要证明：它能在那次真实错误上失败。
- 修改全局规则文件属于"先问"。
- 回复写出：每类错误的证据、选了哪一层，以及为什么更高的层级不行。

## 4. 两个遗留问题

### 4.1 临时文件写到 `/tmp`

SKILL.md 授权段改为明确的路径约定：
1. 宿主提供了会话临时目录时（Claude Code 会在系统提示里给出 scratchpad 路径），用它。
2. 没有时，用仓库根目录的 `.dflow/tmp/<日期时间>/`。创建前确认 `.git/info/exclude` 里有 `.dflow/` 这一行，没有就追加。这个文件只在本仓库本地生效，不进提交。
3. 不使用 `/tmp`，也不使用 `$TMPDIR` 的根目录。

收尾时：
- 关掉自己启动的进程；
- 删除自己创建的非证据临时文件；
- 保留证据目录，并在回复里写出它的路径。

验证技能生成模板 `references/create-verification-skill.md` 里，证据目录的默认值同步改为按上面的约定取路径。

### 4.2 提交信息语言

提交规则后加一段：
1. 仓库规则文件（AGENTS.md、CLAUDE.md、CONTRIBUTING）写了语言的，按规则。
2. 否则看最近 10 条非合并提交的 subject，忽略 `type(scope):` 前缀，跟随多数语言。
3. 平票或没有历史时，用英文。

## 5. Codex 可用

- **安装**：`install.sh` 把 `skills/dflow` 链接到 `~/.agents/skills`（Codex 读取）和 `~/.claude/skills`；`skills/dflow-report` 链接到 `~/.codex/skills` 和 `~/.claude/skills`。
- **兼容**：
  - `disable-model-invocation` 是 Claude Code 的字段，Codex 会忽略，所以 Codex 里可能按描述自动触发 dflow。描述末尾的 "Only for explicit /dflow" 改为 "Only when the user names dflow"，减少误触发。
  - SKILL.md 里提到 TodoWrite、ToolSearch 等 Claude 工具的地方，都写成"如果有"。第 1 阶段已经这样做（路由行在没有 todo 工具时照样输出）。
  - 用 codex 做跨模型评审时，在 Codex 宿主里改用一个 Claude 只读会话，例如 `claude -p --permission-mode plan`。不可用时写"未审查"。
- **切换前不动**：devflow-* 的链接保持原样，dflow 和它们并存。

## 6. 路由表和 SKILL.md 变化

路由表新增三行，其余不变：

| 剧本 | 何时 | 文件 |
|---|---|---|
| 影响面 | "影响面""会影响什么""这个改动安全吗" | `references/impact.md` |
| 原型 | "做个原型""哪种效果好""先做出来看看"，或一个界面上的分歧 | `playbooks/prototype.md` |
| 润色 | "润色""去 AI 腔""精简这段文字" | `references/unslop.md` |

路由表下补一句区分规则：按用户要的产出选剧本。
- 要结论清单的，是评审；
- 要讲清楚的，是讲解或调研；
- 要能看的变体的，是原型；
- 要可执行计划的，是方案。

跨模型规则从三处改为四处：在原有三处之外加上评审剧本，并在 Codex 宿主里改用 Claude 只读会话。原则索引不变；"结构化教训"原则的说明里加一句，以 `slop-check.sh` 为例。

## 8. 验收

**方法**：
- 和第 1 阶段一样，每项在演示仓库的全新克隆里，用新会话跑 `/dflow …`（Codex 项用 `codex exec`）。
- 第 1 阶段的证据只记了文件名，会话结束后无法复核。这次每项在 `docs/acceptance/stage2/<项>.md` 写一份可提交的摘要，包含：
  - 请求原文；
  - 基线 SHA 和结束时的 SHA；
  - 关键命令及其退出码和关键输出；
  - 最终的 `git status`、远端引用、新增文件清单；
  - 费用。
- 完整会话记录体积大，不提交，摘要里写它的路径和 SHA256。

**各项**：
- **A6 评审**：`/dflow 评审 docs/plan-*.md`。通过条件：
  - 会话记录里有真实的 `codex exec` 调用和输出文件；
  - 第一行写了评审模型；
  - "必须改"不超过 5 条，每条有位置和最小修改；
  - 没有改文件。
- **A8 调优**：给一个真实发生过两次的纠正："修改了没让改的全局规则文件"。通过条件：
  - 提出比文字规则更高的层级，或说明为什么做不到；
  - 新检查在那次错误的复现上实际失败过；
  - 改全局文件前先问了。
- **A10 影响面，显式**：演示仓库里预置一个提交，改了公共函数的返回格式；另有一个文件读取该格式。请求 `/dflow 这个改动会影响什么`。通过条件：
  - 指出了那个调用方；
  - 安全依据标了证据等级；
  - 至少一条结论是"跑过证明"，并附脚本输出。
- **A10b 影响面，自动**：`/dflow 把 total 的返回值改成字典`，不提"影响面"。通过条件：
  - 走实施剧本，提交前自动做了影响面检查，发现了预置的调用方；
  - 收尾报告里有固定的"影响面："一行。
- **A11 去 AI 腔**：给一段预置了 10 处 AI 腔的中文文档，请求 `/dflow 润色 docs/x.md`。通过条件：
  - 修改后每个未豁免的命中，要么已改，要么有保留理由；
  - 数字、否定、范围、责任方和来源都没有变（逐项对照）；
  - 文件已本地提交；
  - `slop-check-test.sh` 通过。
- **A12 原型**：`/dflow 报表用表格还是卡片展示更好，做个原型看看`。通过条件：
  - 临时目录里有带切换按钮的 HTML，以及每个变体的截图；
  - 给出了推荐；
  - 仓库没有新增文件或提交；
  - 启动的服务器进程已结束。
- **A13 其余剧本**：各跑一次。
  - 进展：只读，开头一句说有几件事需要用户。
  - 交接：提示词包含目标、完成条件、HEAD 和死路，且没有派发。
  - 周报：在同一仓库、同一时间范围，dflow-report 和 devflow-report 输出的事项一致。在 Claude 和 Codex 的新会话里各直接调用一次。
  - 提交与发布：
    - 本地拆分提交；
    - 预置一个无关的已暂存文件，结束后它仍然暂存、没有被提交；
    - 要求开 PR 时先问了，裸远端引用不变。
- **A14 路由对偶**：同一主题用两种说法，检查路由和是否改文件。
  - "解释这个方案为什么可行"应走讲解，且不改文件；"评审这个方案"应走评审。
  - "比较表格和卡片哪个好"可以走讲解或方案，但不应该写原型；"做个原型看看"应走原型。
- **A15 遗留问题**：
  - 在 A10–A13 期间，用 `find /tmp -newer <开始标记> -user $USER` 检查，没有新增文件；
  - 提交信息语言符合 4.2 的规则。演示仓库用英文历史，ludus 那次 B8 会话没有提交，不算在内。
- **A16 Codex**：`codex exec` 在演示仓库运行 "使用 dflow 修复 total 的 bug"。通过条件：
  - 第一行输出了路由行；
  - 不提问，按测试、修复、提交完成；
  - 远端引用不变。

## 9. 不做

- arena 剧本：见 2.4。
- 行为和时序原型：见 2.3。

## 10. codex 评审处理

codex 只读评审（第 1 版）结论为"修改后执行"：0 条 P0、5 条 P1、5 条 P2。主会话逐条核对后的处理如下：

| 意见 | 处理 |
|---|---|
| P1 验收证据不可复核 | 采纳：增加 `docs/acceptance/stage2/` 摘要（第 8 节） |
| P1 自动影响面没有契约和验收 | 采纳：定义触发条件、固定输出行，替换 build 里的原句，增加 A10b |

## 11. 风险

- **剧本变多，路由更容易选错**：用第 6 节的区分规则和 A14 的对偶测试缓解。路由行能让用户一眼看出选错了。
- **去 AI 腔词表误伤**：脚本只报告，并允许豁免。
- **周报单独成技能，与"单一入口"不一致**：为了 Codex 能直接调用，接受这一点。
- **影响面的"跑过证明"在没有测试环境的项目里做不到**：此时如实标"指到代码行"或"未证明"，不降低标准去冒充。
- **宿主差异**：Claude Code、`claude -p` 和 Codex 的工具不一致（第 1 阶段已出现 `-p` 里没有 todo 工具的情况）。截图、临时目录、技能发现都靠 A12、A15、A16 分宿主验证。
- **验收覆盖面**：演示仓库很小，无法证明在复杂仓库或已有脏工作区里同样成立。这要靠试用期（E1）。
