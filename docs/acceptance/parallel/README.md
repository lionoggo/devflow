# 并行实施验收（2026-10-14 至 15）

方案：`docs/plan-dflow-parallel.md`。演示仓库 `sales-report`：方案 `docs/plan-formats.md` 含 U0 接口、U1–U3 三个格式化器（互不相交）、U4 打包（依赖 U1、U2）、共享文件 README 和 `app/formats.py`。

## 第 0 步实测

- 从链接 worktree 派子 agent：worktree 建在**主仓库**的 `.claude/worktrees/` 下。
- 子 agent 的 worktree 从仓库默认分支的最新提交拉出，不是当前 HEAD。从链接 worktree、从 `dflow/<slug>` 分支派发都是这样。任务说明因此要求 worker 先切到 base，`scope`、`land` 也检查祖先关系。
- 会话被杀：后台子 agent 一起结束，没有留下提交。worktree 可能消失，也可能以 locked 的空状态留下（两次实测各见一种）。

## 结果

| 项 | 运行 | 结果 |
|---|---|---|
| P1 吞吐检查 | 顺序 `seq`、小方案 `small`、无人值守框定 | 通过：三处都写出"并行：不适合"及原因（单元不到 50 行、检查不到 1 秒；小方案不到 30 行）。没有出现"可拆 N 路"的正向建议，因为这个方案的单元都小于门槛 |
| P2 并行执行 | `par`（"按方案并行实施"） | 通过：U1–U3 在同一条消息里以 3 个后台 worktree 子 agent（sonnet）派发；U4 在 U1、U2 落地后才派发，base 是 U2 落地后的 HEAD |
| P3 落地与集成验证 | `par` | 通过：每个单元恰好一个提交；每次落地后在主目录跑测试；共享文件最后统一提交；主会话的集成检查另外发现并修了 `-0.00` 的显示问题 |
| P4 冲突 | 脚本测试 | 通过（`parallel-test.sh`）。真实运行里没有出现冲突，因为共享文件已从单元里拿出，按设计冲突应该很少 |
| P5 越界 | 脚本测试 | 通过（`parallel-test.sh`）。真实运行里没有越界的单元 |
| P6 清理 | `par`、`un` | 通过：`par` 结束后只剩主目录 worktree；`un` 被杀会话留下的两个空 worktree 没有登记，被列为遗留并在回复里报告，没有删除 |
| P7 子 agent 危险命令 | `par` | 通过：扫描读取了 4 个子 agent 的记录，标出了它们改分支名的 `git switch -C unit-…`，以及主会话用于反证测试的 `git stash`。这暴露了两个缺陷，都已修复：任务说明的准备命令写法不清；在场实施的收尾没有扫描危险命令 |
| P8 无人值守并行与接手 | `un`（tmux，"开始，并行"） | 通过：U1–U3 派发后杀掉会话；新会话接手时停掉旧会话的租约，把 3 个已派发的单元重新派发并各自落地，U4 由主会话按顺序做，收尾"完成"；危险命令"无"；决策日志里有 worker 的决策行，证据标了 `agent-<id>` |
| P9 成本对比 | `seq` 对 `par`，同一方案 | 顺序做 110 秒、$0.58；并行做 503 秒、$1.94。并行慢了 4.6 倍、贵了 3.3 倍。这个方案的单元都很小，验证了"小单元不适合并行"的判断和门槛。大单元时并行是否省时间，还没有测 |

## 验收中修掉的问题

1. 任务说明的准备命令含糊，worker 改了分支名，结果被扫描标成危险命令；主会话又手工删除遗留分支。现在改为两条直接执行的命令，分支名保持不变（431dba6、c99c779）。
2. 在场实施的决策日志收尾没有扫描危险命令；交给 codex 的时间线被截断。现在扫描子 agent 记录、列出结果，时间线原样交给 codex（431dba6）。
3. 插入新正则时写错引号，`timeline.py` 出现语法错误（7705eb4 修复）。
4. 落地成功后在 `.dflow/` 留下 `.err` 文件（431dba6）。
5. 被杀会话遗留的 worktree 没有被列出。现在 `cleanup` 把未登记的 `.claude/worktrees/*` 列为遗留，只报告不删除（c99c779）。
