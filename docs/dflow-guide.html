dflow 使用说明

一个入口，说出你要的结果；它按意图选流程，可撤销的步骤直接做，收尾给出能核对的证据。在 Claude Code 和 Codex 里用法相同。

它是什么

dflow 参照 pstack 的 poteto-mode 重做：不再是一堆要记名字的 skill，而是一个入口加 18 个流程（playbook）。你不用选流程，用自然语言说目标就行。它坚持几条原则：

不停下等人

改代码、本地提交、在可行做法间取舍，直接做，做完告诉你选了什么、怎么改回。

小步可验证

每个单元做完就验证、就提交，不攒到最后。

真实证据

“完成”要附命令输出、截图或真实路径上的观察；没跑过的检查不会说跑过。

对齐原目标

验收对照你最初的要求逐项核对，不拿“测试全绿”代替。

怎么调用

宿主主入口直达复盘直达周报
Claude Code/dflow <你要做的事>（等同 /dflow:dflow）/dflow:retro/dflow:report
Codex$dflow:dflow <你要做的事>$dflow:retro$dflow:report
  • 默认说自然语言：/dflow 登录页白屏，截图在这。它会按意图选“排查”。
  • 想点名流程：第一个词写流程的中文名或 id，例如 /dflow 复盘 全部、/dflow debug 登录页白屏。只看第一个词。
  • Codex 注意：只写 $dflow 不会进入 dflow，要写 $dflow:dflow。
改了插件源码之后：Claude Code 在会话里 /reload-plugins 或开新会话；Codex 要先执行 codex plugin add dflow@devflow，再开新会话（Codex 用的是复制出来的缓存）。

它替你做什么、先问你什么

直接做，做完说明先问你
改代码、写测试、本地提交；在几种可行做法里选一种；跑检查；在临时目录做实验 push、开 PR、合并、rebase、改写历史；删除或覆盖不是它这次创建的东西（含未跟踪文件）；外部发布；偏离原目标的做法；产品方向和偏好
  • worktree 授权：你说“并行”或“多线”，或明确要求“在不同的 worktree 里做”，就等于同意它为这次任务建、删 worktree。没说的话，它只会给出拆分计划，再请你说“多线”。
  • 丢数据前一定列清单：哪怕你说“清理一下”，它也会先列出会丢的具体文件，等你确认。
  • 安全提示不代按：比如可见窗口里 Claude Code 的“信任此文件夹”提示，它不会替你确认。

能力地图

理解与设计

讲解teach

想弄懂一个概念、方案或已知代码：为什么、是什么、怎么想。

调研research

需要带证据查清：现有代码怎么工作、为什么这样做、业内怎么做。复杂问题会分角度并行探索。

方案plan

把想法变成可批准的方案：需求、方向、结构、怎样算完成。不在这里动手实现。

评审review

审方案或代码、比较两种做法；产出是一份问题清单。

原型prototype

“哪种效果好”“先做出来看看”：做几个界面变体对比。

影响面impact

“这个改动会影响什么”“安全吗”。

动手与验证

排查debug

报错、失败、“仍然…”、截图加症状。先在你看到的地方复现，再定根因、修、复验。

实施build

按批准的方案一个单元一个单元做，每个都验证并提交。只说“并行”时，独立单元交给同宿主子 Agent。

验收verify

对照原目标逐项、走真实路径核对。单独验收只出报告；说“验收并修”才会修。

提交与发布ship

整理、拆分提交，写提交信息；开 PR、推送前先问。

多会话与长时间运行

多线lines

把一件事拆成几条线，分给 Claude/Codex 各自的 worktree；本会话收回执、换模型验收、按提交号落地。

无人值守unattended

“去睡了”“跑到…为止”：先定完成条件、截止时间和范围，你说“开始”后一轮轮推进，不再停下等你。

交接handoff

写一份新会话能直接接手的完整说明；交出去后本会话不再管。

进展status

只读：每件事做到哪、卡在哪、等你决定什么。

回看与维护

复盘retro

“昨晚做了什么”：审一次带决策日志的运行，先给值得看的，再指向具体记录。

周报report

按时间范围从 Git 汇总你的工作，默认最近 7 天。

调优tune

改 skill、AGENTS.md、CLAUDE.md；把反复出现的错误写成规则或脚本。

润色polish

去 AI 腔、精简文字。

并行、多线、交接：按“谁负责”区分

流程谁对结果负责典型说法完成怎么算
实施里的并行本会话；单元来自同一份方案“方案定了，你来改，并行”子 Agent 的最终报告 + 本会话落地并跑检查
多线本会话一直负责：登记、收结果、验收、落地“启动两个可见 Session，在不同 worktree 做”“让 Codex 做 Web，你做 3D，最后你来合”回执文件 + 另一模型的验收 pass（按提交号）+ 落地
交接交出去后归对方“交给新会话继续做”对方接手，本会话停止写入
评审（跨模型也一样）本会话“让 Codex 审一下这个方案”一份问题清单

多线默认在后台跑（Claude 用子 Agent，另一个模型用 headless）；你说“可见”或“开窗口”，或某一步需要你在窗口里操作，才开可见窗口。

使用案例

下面的案例按你最近的真实工作方式写。每个案例分四部分：你怎么说、它会怎么做、你会看到什么、要注意什么。

排查1 地图房间位置不对

/dflow [截图] 这个房间的位置和感觉好像还是不对，分析下根本原因
它会怎么做
  1. 先在你看到问题的地方复现：启动游戏或跑出同一帧，确认看到的和截图一致。复现不了会加条件、加日志，直到触发。
  2. 列出几种可能原因，用运行时证据逐个排除（日志、坐标打印、对比好的版本 git show <rev>:<path>），不靠猜。
  3. 修在根上，并检查其他房间或项目有没有同样的模式，一起修。原因是数据或配置时，改数据或给恢复步骤，不改代码。
  4. 能便宜地写测试时，先写一个会失败的测试，再修。
  5. 回到同一个界面复验，附截图或输出。
你会看到

根因一句话、证据位置（文件:行号或截图）、改了什么、复验结果、同类问题是否一并处理。

只想知道原因、先别改代码：加一句“先别改代码”，它在定位完根因后就停。

调研方案2 从一个想法到可批准的方案

/dflow 素材平台导出太慢，我想加缓存，业内一般怎么做
它会怎么做
  1. 先把需求和手段分开：“导出慢”是需求，“加缓存”只是一种手段。
  2. 事实问题自己查（代码、配置、跑一次计时），必要时在临时目录做小实验；只问你产品或偏好问题，最多三个。
  3. 对比几条方向（含业内做法），给出推荐和理由；需要新模块或公开接口时，先给结构草图。
  4. 写出可执行的方案：分哪些单元、每个单元怎么验证、怎样算完成。
你会看到

一份方案（长的会存成文件），末尾是验收条件。它不会在这一步动手实现，等你说“开始”或“你来改”。

想让另一个模型挑刺：接着说“让 Codex 审一下这个方案”，这走“评审”，不是多线。

实施验收3 按方案实施，再独立验收

/dflow 方案没问题，你来改
它会怎么做
  1. 先判断能否拆成独立单元（吞吐检查）；不适合并行就按顺序做，不会停下来问。
  2. 每个单元：改代码 → 跑这一单元的检查和已完成阶段的检查 → 本地提交（type(scope): subject，不超过 72 字符）。
  3. 收尾说明影响面，并请另一个模型做一次审查（看缺失需求和弱测试，不只看 diff）。
/dflow 验收一下，重点看动画是否连续、玩法是否完整
  1. 以你的原始要求和批准的方案为标准，逐项建验收矩阵。
  2. 用户可见的结论要在真实路径上观察：动画看连续片段，不拿单帧代替；玩法逐条走。
  3. 失败分类：产品缺陷、测试工具问题、环境问题、基线本来就失败。
单独说“验收”只出报告、不改代码。想让它顺手修，说“验收并修”；同一会话从实施走到验收的，会自动修小问题，同一缺陷最多三轮。

实施·并行4 同宿主并行几个独立单元

/dflow 方案定了，你来改，并行
它会怎么做
  1. 写出拆分：先做的公共部分、可独立的单元（写入路径互不重叠、单独落地也能跑能验）、共享文件（最后由它自己改）。
  2. 每个独立单元派一个后台子 Agent，各自在 worktree 里做，最多同时 3 个。
  3. 每个单元回来后：范围检查 → 落到主工作区 → 跑检查 → 通过就提交一次；不通过撤回并带着原因重派。
  4. 全部落地后删掉对应 worktree；有未提交改动或被忽略文件的会保留并列出来。
你会看到

一行总结：并行：N 路，落地 X 个单元，退回 Y 次，保留的 worktree：…

耦合的工作不会硬拆：比如角色状态机和它的动画控制器，文件不重叠也算一个单元。

多线5 Claude 和 Codex 分工，互相验收后合入

/dflow 把设计、Web、3D 三块拆开，分别交给 Claude 和 Codex 在各自 worktree 里做，做完让另一个模型验收，再按顺序合进 main
它会怎么做
  1. 定框：完成条件写成可计数的（“3 条线都已落地，每条在来源提交上有 pass”）、线数、时间预算。一个 Agent 就能在预算内做完的，退回普通实施。
  2. 建账本：清单 .dflow/<slug>.md（允许写和受保护的路径），线表，常驻指令 standing.md（每条线的 brief 都会原样附上）。
  3. 试点：先完整跑通一条线，修正 brief 模板和验证方法，再派其余的。
  4. 派发：每条线一份 brief（目标、范围、验收项和一个“测试绿但你仍会不满意”的反例、时限、回执路径）。默认后台：Claude 线用子 Agent，Codex 线用 headless，headless 线自带截止时间。
  5. 收回执：worker 写完回执文件才算交付；中途的提交只算进展。
  6. 验收：只要一条命令能验证的，worker 自报、你抽查；动画、手感、影响面大的，派另一模型家族的验收线。同一提交上出现过 fail，后面的 pass 盖不掉，修复必须产生新提交。
  7. 落地：land 自己检查范围、清单、验收账本和回执，任何一项不过都不落地；提交后关闭落地记录。
  8. 收尾：共享文件最后作为一条线落地，然后在最终 HEAD 上逐项核对整个清单。
中途你可以
  • 问进度：/dflow 进展，它只读地给出看板并现场核对 git 和进程。
  • 改方向：直接说。运行中的线不接受传话，它会停掉这条线，带着完整范围重开一个新的尝试（旧尝试的有用提交会保留下来）。
  • 要看着某条线：说“这条开可见窗口”。新 worktree 里的 Claude 会先弹“信任此文件夹”，需要你亲自确认。
共享资源（Godot 窗口、浏览器、设备、外部账号）写进常驻指令后，各线要拿机器级锁才能用；拿不到就不做那一步，并在回执里说明。

无人值守6 睡前交代，早上收结果

/dflow 我去睡了，把 P2 的三个阶段做完并验收，早上 8 点前结束
它会怎么做
  1. 只停这一次：给你一屏定框，包括每个完成条件的命令、预期结果和现在的基线输出，还有单元顺序、分支、允许写和受保护的路径、截止时间。然后等你说“开始”。
  2. 你说“开始”后：领租约（防止两个会话同时跑）、开防休眠、写决策日志，进入循环。
  3. 每一轮：核对现场 → 挑风险最高的未完成单元 → 做一小步 → 跑检查 → 有进展就提交，没进展就回退并记录。
  4. 到截止时间、全部条件通过或真正卡死时收尾：重跑全部条件、跨模型审查、写结论（完成 / 部分完成 / 受阻）、通知你。
你会看到

早上一条通知，加一份按条件计数的总结。需要你决定的事情会集中列在最后，不会半夜把你叫醒。

“去睡了”“别停”不会触发暂停；想停说“暂停”或“先停一下”。在 Codex 里，循环只在交互会话（App、IDE、TUI）里能持续，codex exec 跑完第一轮就会结束。

进展复盘7 早上回来：现在怎样，昨晚做得对不对

/dflow 进展

只读汇总：每件事的结果、证据、还在跑的线、等你决定的事。不会改任何文件，也不会去停任何 worker。

/dflow 复盘 全部

审查最近一天写过决策日志的每次运行：先列出值得你看的（偏离目标、跳过的检查、可疑的“完成”），再指向具体日志行和提交。只说“复盘”审最新一次；/dflow:retro <slug> 审指定那次。

交接8 上下文太长，交给新会话

/dflow 写一个交接 prompt，交给新的 Codex 会话继续做剩下的
  1. 钉住现场：仓库绝对路径、分支、HEAD、未提交和未跟踪文件、需要的准备步骤。
  2. 写清目标、已完成和已验证的部分、剩下的第一步、走不通的路，用接手方能看懂的词。
  3. 先给你看；你说发才发（Orca、新会话或子 Agent）。发出后本会话停止写入。
如果你还想让本会话继续收结果、验收、合入，那不是交接，说“多线”。

调研验收9 代码转策划这类非代码交付

/dflow 把参考游戏的战斗系统从代码整理成策划文档，覆盖所有技能和数值来源，完成后让 Codex 独立核对
  1. 先定“覆盖所有”的口径：列出代码里的技能清单和数值入口，作为验收矩阵。
  2. 按模块整理，每条结论附代码位置（文件:行号），推断出来的标成推测。
  3. 交付物是文档路径，不是提交号；在多线里它是一份只读回执，不会被“落地”。
  4. 独立核对逐项对照矩阵；漏一项就记为未验证，不算通过。

周报润色调优10 周报、润色、把错误写成规则

/dflow:report 最近两周，最后给一段 300 字的重点总结

按你的提交作者邮箱汇总提交和方案文档的变更，每条可追溯到提交。

/dflow 润色这段 README，去掉 AI 腔
/dflow 它又在没跑测试的情况下说“已验证”，让这个错误不可能再发生

“调优”先确认这类错误至少出现过两次（只发生一次不算教训），再按这个顺序选最高的一层：从结构上去掉错误做法 → 加检查（类型、lint、脚本、hook）→ 行为测试 → 最后才写成文字规则。新检查要先在复现的旧错误上失败、在改正后通过。直接让它改 skill、AGENTS.md 或 CLAUDE.md 也走这个流程。

一周试用计划

当前版本已冻结（本地标签 dflow-trial-2026-10-25）。这一周只修会阻断使用的 bug，不加功能。

顺序任务主要观察
1两个 30–60 分钟的短任务：一个直接实施，一个轻量并行调度是否真的省时，有没有拖慢
2真实双线：一条实现，另一模型验收；故意经历一次失败、修复、重验协调消息是否减少，fail 是否闭环
3一次非代码交付（代码转策划或分析）回执是否被误当成验收
4一次需要 Godot 或浏览器的检查资源锁、焦点冲突、清理
5一次 4–8 小时过夜任务早上能否一页看懂
6在安全边界退出后冷恢复是否重做已有工作或重复昂贵检查

只记六个指标：协调性消息次数、空等时长、第一份可接手产物的时间、宣布完成后发现的原目标遗漏、流程开销占比、恢复时的重复执行。

常见问题

它为什么不停下来问我？

可撤销的事情它直接做，并在回复里写明选择和改回方法。真正需要你决定的（产品方向、偏好、不可逆操作）它会集中列出来。

“并行”和“多线”我该说哪个？

一份方案内部的小单元、同一个宿主就够：说“并行”。要跨会话、跨模型、开可见窗口，或者另一个模型来验收：说“多线”，或直接用自然语言描述这种分工。

能在运行中的线里插一句话吗？

不能，这是有意的：中途传话容易丢指令，也会出现两个写入方。要改方向，它会停掉这条线，带着完整范围重开。

可见窗口卡住不动？

多半停在“信任此文件夹”提示上，需要你亲自确认。不想处理这个，就用默认的后台方式。

怎么知道它说的“完成”可信？

看三样东西：验收矩阵是否逐项有证据；多线里每条线的验收账本是否在来源提交上有 pass；收尾是否在最终 HEAD 上重跑了全部条件。

关于改名

名字应该表达 dflow 的核心定位，而不是其中某个流程。Codex 给出的定位是：用户定目标，插件选流程，在授权范围内主动推进，并用证据收尾的一种个人开发工作方式。pstack 的 poteto-mode 靠作者名表达“这是一种工作方式”；换成通俗名字，名字本身就要承担这层解释。

候选中文叫法调用优点风险
banfa（Codex 推荐第一）办法/banfa · $banfa:banfa最像“一种工作方式”，能装下全部 18 个流程；5 个字母执行感弱，听起来像只出主意，需要配副标题
tuijin（第二）推进/tuijin最贴近“不停下等人、主动推进”体现不出选流程和用证据收尾，有点项目管理的味道
youshu（第三）心中有数/youshu贴近账本、进展、证据收尾，有品牌感容易被理解成数据或报表；已有同名中文品牌
gongfa工法/gongfa就是“成套方法与步骤”偏施工；口头容易听成“功法”
luoshi落实/luoshi强调落到结果偏执行，盖不住讲解、调研
dangjia / zhanggui当家 / 掌柜/dangjia形象，适合多会话照管暗示替你做主，和“方向由你定”有冲突
banli / banhao办理 / 办好/banli通俗、短行政手续感重；“办好”口气像打包票
stride迈步/stride有持续推进感已有 Stride 游戏引擎等同名产品，不建议用
dflow（保留）开发办法/dflow不用迁移；也说得通（development flow）d 的含义不直观；flow 偏向流程编排

以上候选都没有联网查重，正式使用前需要先查一遍。

如果要改，只改对外的名字：插件名、主入口名、调用示例。内部协议全部保留：各仓库里的 .dflow/ 账本、dflow 线 标记、DFLOW_* 环境变量、refs/dflow/、源码目录 plugins/dflow/，以及 marketplace 名 devflow。这样旧的运行记录照常能恢复，撤回也只需回退一次提交。旧调用 /dflow 不会自动保留，要想继续用，得单独做兼容入口并在两个宿主里分别验证。
时机：建议一周试用结束后再改。试用期间先在心里换着叫叫看，比如“用办法跑一下”“让它推进”，看哪个说起来自然；现在就改名，会让试用前后的数据没法比。
