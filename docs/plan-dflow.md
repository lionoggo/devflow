# 方案：dflow，按 pstack 的形状重建开发流程

> 状态：待用户批准（第 2 版：改为 pstack 的"不停下等人"）。日期 2026-10-14。worktree `devflow-dflow`，分支 `dflow`（基于 main a471776）。
> 依据：
> - `docs/pstack-analysis/README.md`：pstack 源码分析汇总，四份分组报告在同目录；
> - `docs/pstack-analysis/history-mining.md`：8064 条用户历史消息的统计；
> - `docs/plan-unattended.md`：无人值守底稿，本方案吸收并修订。
>
> 用户已决定：
> - 放弃 devflow-* 体系；
> - 本地提交直接做，push、开 PR、合并、对外发送仍先问；
> - 默认精简；
> - 在本 worktree 开发，跑通后再停用 devflow；
> - 技能名以 `dflow` 开头。

## 1. 为什么这样设计

devflow 偏手动，根源有三：
- 没有统一入口，七个技能各靠描述自动触发，衔接靠用户；
- 每个技能都在关键处停下来等人；
- 无人值守靠一套仪式，卡住就收尾。

pstack 不手动，靠的是五件事：
- 一个入口，加剧本步骤进 todo；
- 原则词表；
- 验证先行；
- 卡住不停；
- 把错误变成结构。

第 1 版方案根据历史统计（"没先说清楚就动手"168 次、"不确定就问我"69 次）设了一个开工前的确认门。用户否定了这一点：那些纠正是在 devflow 默认会动手的前提下产生的，用户希望采用 pstack 的工作方式。核对 pstack 源码后，这个方式成立的前提有三点：

1. **只对可撤销的工作不停**（`principle-never-block-on-the-human`）：写代码、拆任务直接做；force-push、删数据、对外发送仍然要确认；产品方向来自人。本地提交直接做，加上每个单元都提交，保证一切可回退。
2. **停不停由用户在提示里说**：pstack 把"先别改代码""let me review before proceeding"当作用户的约束（`docs/guide/02-poteto-mode.md:48`），流程默认不停；只有长时间运行前给一次框定（`figure-it-out/SKILL.md:23`）。
3. **agent 必须能自己验证**："先赢得信任再开循环"，否则只是更快地产出没验证的东西（`docs/guide/07-overnight.md`）。所以验证排在第一阶段，包括为项目生成验证技能。

dflow 的核心规则因此是：**可撤销的工作直接做完再报告；不可逆、对外、丢数据的操作才停下问；用户想先看方案时在提示里说一句。**

## 2. 计划

**目标**：
- 用户用 `/dflow <一句话>` 开始任何非琐碎任务。dflow 自己判断这是哪类事、按哪个剧本走，用户能在 todo 里看到每一步。
- 需要改东西的任务只停一次确认，之后一直做到有真实证据的完成，包括本地提交。
- 用户离开时说一句话，dflow 就跑到完成条件或真正的死路。
- 反复出现的纠正能被沉淀成检查或规则。

**非目标**：
- 不搬 pstack 的团队规模部分（Autopilot、Orchestrate、Shipping、benny）、Cursor 专属部分（Custom Mode、云端子 agent、模型配置技能、多模型面板）、英文写作规则；
- 不做进展页，不做结构性守卫；
- 不在停用 devflow 之前改动 main 上的 devflow 技能。

### 2.1 决定

1. **一个技能，内含剧本和原则**：
   - 只建一个技能 `skills/dflow/`，`disable-model-invocation: true`，用户输入 `/dflow` 时加载。
   - 结构照 pstack 的 poteto-mode：`SKILL.md` 只放路由表、原则索引、授权边界、回复规则；剧本在 `playbooks/*.md`，原则细节在 `principles/*.md`，脚本在 `scripts/`。
   - 不再拆成多个可独立触发的技能，避免像 devflow 那样互相抢路由。

2. **入口流程**：
   1. 复述目标。如果是长讨论之后，先说"我理解的目标是…"。
   2. 按路由表匹配一个剧本。
   3. 把剧本步骤原文抄进 todo，跳过的步骤写 `跳过：原因`。
   4. 按剧本执行。
   5. 用中文收尾报告结束。

   用户说"新任务"时重新匹配剧本。同一会话里的短跟进（"继续""你来改""好的"）沿用当前剧本。

3. **路由表**（依据历史占比）：

   | 剧本 | 何时 | 历史依据 |
   |---|---|---|
   | 讲解 | 想弄懂某个概念、方案或代码：为什么、是什么、怎么理解（学习用途） | 22%；对应 pstack teach（how + why） |
   | 调研 | 调研现有代码或项目怎么工作、为什么这样设计、业内怎么做，没有故障现象 | devflow-research；采用 pstack how、why 的置信分级 |
   | 排查 | 报错、失败、"仍然"，或给了地址、截图加现象 | 7.7%，点名 176 次 |
   | 方案 | 想法、方案、选型、"业内怎么做" | 21.5% |
   | 评审 | 评审方案或代码、对比两个方案 | 288 条，要求独立评审 97 次 |
   | 实施 | 方案已批准，或"你来改" | 8.2% |
   | 验收 | 验收、真实端到端 | 9.4%，点名 211 次 |
   | 无人值守 | "我要离开 / 去睡了 / 跑到…为止 / 别停" | 0.9%，但正是这次的痛点 |
   | 交接 | 要交接提示词、开新会话、派给其他 agent | 4.6% |
   | 进展 | 问进展、下一步、为什么停了 | 3.3% |
   | 周报 | 按 Git 记录汇总一段时间的工作进展 | devflow-report，用户常用（历史统计未抓到其真实用量） |
   | 提交与发布 | 提交、拆分提交、开 PR、跟进 PR | 5.2% |
   | 调优 | 修改技能、AGENTS.md、CLAUDE.md，或"把这个错误变成规则" | 约 138 条 |

   都不匹配时，按"方案"处理：先框定目标和完成条件。

4. **不停下等人**（照 pstack）：
   - 可撤销的工作直接做完再报告，包括改代码、本地提交、跑检查、拆任务、在多个可行做法之间选一个。选择写进收尾报告，并说明用户可以怎么改。
   - 能用实验回答的分歧，先做原型或实验，用结果决定，不问用户（pstack Prototype）。
   - 只在三种情况停下：
     - 下一步是授权边界里需要先问的操作；
     - 产品方向或偏好问题，实验无法回答：先做不依赖它的部分，实在没有可做的，按默认推进并标明；
     - 真正的死路。
   - 用户在提示里写了约束（"先别改代码""先给我看方案""改完先别提交"），按约束执行，这一次覆盖默认。
   - 改动东西的剧本，开工时用两三行说明目标、完成条件和做法，然后直接开始，不等回复。只有预计运行超过一小时的任务，才停一次给出框定（照 figure-it-out）。

5. **授权边界**（写进 SKILL.md，覆盖剧本里的任何说法）：
   - **直接做**：读、搜索、运行检查；修改目标范围内的文件；在当前分支本地提交（按功能拆分，提交信息 `<type>(<scope>): <subject>`）；撤销本次运行自己做的改动；在 scratchpad 里写临时脚本。
   - **先问**：
     - push、开 PR、合并、rebase；
     - 改写历史（amend、reset、force）；
     - 创建、切换或删除 worktree；
     - 删除或丢弃未提交的工作、删除未跟踪文件：先列出具体内容；
     - 写到外部系统（工单、聊天、发布）；
     - 修改不在本次目标里的文件，包括全局规则文件；
     - 删除或改写用户在本次运行之前就有的未提交改动。
   - 子 agent 只在能实质降低总成本时用，默认 Opus 或更低。跨模型审查用 `codex exec -s read-only`，只在三处默认启用：
     - 方案定稿前；
     - 排查第二次失败时；
     - 无人值守收尾时。
     其余场景由用户要求时才用。

6. **原则**（约 10 条）：SKILL.md 只放索引，每条一行"何时适用 + 一句规则"，细节在 `principles/`。来源是 pstack 的高价值原则，与用户历史纠正对齐：

   | 原则 | 何时 | 规则 | 依据 |
   |---|---|---|---|
   | 不停下等人 | 想问"要不要做 X"，而 X 可撤销 | 直接做，做完说明为什么、怎么改回；方向性问题才问 | 用户决定；never-block-on-the-human |
   | 对齐目标 | 每次回复，尤其长讨论后 | 先复述目标再给结论；发现偏了先说 | E、N |
   | 真实证据 | 宣布完成前 | 用真实运行证明；没跑过写"未验证"；能自己跑的不交给用户 | C、F；pstack prove-it-works |
   | 找根因 | 排查 | 先复现，再找根因；第二次失败就质疑前提、换思路 | F；fix-root-causes、attack-the-premise |
   | 通用解 | 修复和设计 | 说明对其他输入是否成立，不硬编码个例 | A |
   | 先减后加 | 方案、评审、技能设计 | 删除优先、复用优先，新增机制要说清楚为什么现有的不够 | D；laziness、subtract |
   | 测行为 | 写或保留测试 | 断言真实行为；函数全返回空仍能通过的测试要改或删 | test-behavior |
   | 小步可验证 | 多步工作 | 每个单元以检查结束，过了再做下一个 | sequence-verifiable-units |
   | 解释数字 | 报告测得的数字 | 先找出限制它的因素，确认测的是要测的东西 | explain-the-number |
   | 以现状为准 | 引用文档或旧方案 | 先用当前代码核实；缺证据就向用户要，不编造 | J、H、M |
   | 结构化教训 | 同一纠正第二次出现 | 优先改成检查、脚本或结构，最后才写文字规则 | L；encode-lessons |

7. **回复规则**：中文；结论先行；短；举例；不用自造术语或内部编号；每个结论带证据或标明是推测。逐条修订时按 P0/P1/P2 列出，附位置和最小修改。

8. **各剧本要点**：每个剧本 10 到 40 行，先照搬或改写 pstack 对应文本，再补用户偏好：

   | 剧本 | 主要来源 |
   |---|---|
   | 讲解 | pstack teach：先给最小完整答案（一两句），用户追问再加层；先说通用定义再落到当前案例；三个以上部件用逐张叠加的图（Mermaid）；不出题、不说教；保留 why 的置信措辞；中文 |
   | 调研 | pstack how、why：置信分级，"代码不能证明自身意图"；devflow-research 的回答形式；需要外部资料时按 devflow-plan 的 prior-art-research |
   | 排查 | pstack bug-fix、tdd、fix-root-causes；devflow-debug 的现象→证据→原因；通用性检查；找到根因后直接修复、验证、提交（用户写了"先别改代码"时只给根因和方案） |
   | 方案 | devflow-plan：三阶段、plan.md 形状、方案存 docs；加 pstack prototype（能用实验回答的分歧先做原型）；定稿前 codex 审查 |
   | 评审 | pstack interrogate 的评分标准和负责人分档：Act on 不超过 5 条，其余列入 Dismissed；默认 codex 独立评审，评审方不看作者的结论 |
   | 实施 | devflow-impl 的计划纪律；pstack feature 的小步提交；风险改动先做 blast-radius；不强制委派 |
   | 验收 | devflow-verify 的验收体系；pstack create-verification-skill（项目没有验证技能时，提议生成一个）、benchmark-checklist |
   | 无人值守 | `docs/plan-unattended.md`，加上第 3 组报告的 14 条修订（见决定 9） |
   | 交接 | devflow-impl/references/handoff.md；先给用户看提示词，确认后再派发 |
   | 进展 | pstack ketchup 的追赶摘要：读日志、git log、todo，几行说清做到哪、卡在哪、下一步 |
   | 周报 | devflow-report 原样迁移（Codex 也可用） |
   | 提交与发布 | devflow-commit 的安全规则；pstack opening-a-pr 的正文模板、babysit、watch-pr、bugbot 分诊；push 和开 PR 先问 |
   | 调优 | pstack correct（修正层级、"出现两次才算一类"、证明新检查能在过去的错误上失败）、reflect 的筛选标准、authoring-a-skill |

9. **无人值守**：以 `docs/plan-unattended.md` 为底稿，按第 3 组报告修订后并入 `playbooks/unattended.md`：
   - 完成条件可以是有序阶段，直接取自批准方案的阶段；
   - 死路按单元判定：一个单元换过思路仍走不通，就标为死路，转去做别的单元；所有剩余单元都走不通才停；
   - 只有用户能做的决定：先做不依赖它的单元；实在没有可做的，才按默认推进，提交信息标 `default:`；
   - 每轮开头先处理上一轮遗留的未提交改动，并核对 HEAD 和日志里最后一次提交一致；
   - 暂停与新会话接手（核对分支、HEAD，重跑完成条件，写 `start` 行）；
   - 收尾时用 `git diff --name-only <基线>..HEAD` 检测是否改过受保护的测试和脚本，代替运行中的守卫；
   - codex 审查的输入加上对话时间线；
   - 回复末尾加"需要你注意"段。
   - 日志沿用 `.devflow/<slug>.tsv` 的六列，目录改名为 `.dflow/`，`log.sh` 移到 `skills/dflow/scripts/`。

10. **安装**：
    - 仓库的 `install.sh` 按 `skills/*/` 链接。dflow 跑通前只链接 `dflow` 一个技能，devflow 技能不动。
    - 切换时：
      1. 在 `~/.claude/CLAUDE.md` 加一句"非琐碎任务用 `/dflow` 开始"；
      2. 移除 devflow 技能的链接和守卫钩子；
      3. 把 `dflow` 分支并回 main。

      每一步先问用户。

### 2.2 待决事项

无。

## 3. 架构

- **组件**：
  - `skills/dflow/SKILL.md`：负责路由、确认门、授权边界、原则索引、回复规则；不负责任何剧本的细节。
  - `playbooks/<名>.md`：负责一类任务的步骤和收尾格式；不负责授权，统一以 SKILL.md 为准。
  - `principles/<名>.md`：负责一条原则的完整说明和"你跳过了它"的标志。
  - `scripts/log.sh`：决策日志追加。
- **依赖方向**：剧本引用原则和脚本；SKILL.md 引用剧本和原则；剧本之间可以互相转交（例如排查转实施），但不复制彼此的内容。
- **状态**：只有无人值守写 `.dflow/<slug>.tsv`，加本地 exclude；其余剧本不落盘，方案文档除外（写到项目 `docs/`）。
- **变更表**：
  - 新增 `skills/dflow/`、`docs/plan-dflow.md`；
  - 修改 `install.sh`（暂不链接 devflow-*，切换阶段处理）、`README.md`；
  - 删除：切换阶段删除 `skills/devflow-*`。

## 4. 验收

每一项在临时演示仓库里，用新会话真实运行 `/dflow` 验证；能脚本化的，用 `claude -p` 跑，并保存对话记录。

- **A1 路由可见**：`/dflow 这个函数为什么返回空` 匹配"调研"或"排查"，todo 的前几项是剧本步骤原文。验证：对话记录。
- **A2 讲解**：在一段讨论之后问"这个方案为什么通用"，第一段回复是一两句完整答案，追问后才展开；不改文件。验证：对话记录和 `git status`。
- **A3 不停下等人**：在演示仓库报一个能复现的 bug，不加任何约束。dflow 用两三行说明做法后直接开始：复现、修复、跑完成条件、本地提交、收尾，全程不问用户；收尾报告列出它做的选择和改回方法。再用"先别改代码"重复一次，只给根因和方案、工作区无改动。验证：对话记录、`git log`、`git status`、完成条件输出。
- **A4 授权边界**：A3 的仓库带一个本地裸远端，运行结束后远端引用不变；dflow 没有新建 worktree，没有改目标外的文件。验证：`git -C remote.git show-ref`、`git worktree list`、diff 范围。
- **A5 方案**：`/dflow 想给 X 加个缓存` 走方案剧本，产出 `docs/plan-*.md`，定稿前附 codex 审查结论（或写明"未审查：原因"）。验证：文件和对话记录。
- **A6 评审**：`/dflow review docs/plan-*.md` 产出分档结论，Act on 不超过 5 条，第一行写评审模型。验证：回复。
- **A7 无人值守**：`docs/plan-unattended.md` 的 A1–A5，加三项：两阶段完成条件、一个"只有用户能定"的问题和一个与它独立的单元（先做独立单元）、中途杀掉会话后新会话接手不重做。验证：日志、`git log`、对话记录。
- **A8 调优**：给一个过去真实发生过两次的纠正（例如"修改了没让改的全局规则文件"），调优剧本提出最高层级的修法，并说明新检查如何在那次错误上失败。验证：回复和产出的检查。
- **E1 真实试用**：用户在 ludus 用 `/dflow` 做一周日常工作。之后用同样的脚本重跑历史挖掘，比较试用期每百条消息里 B（没先说清楚）、C（假完成）、E（偏离目标）、I（看不懂）、K（中途停下）类纠正的次数，与 8 到 10 月的基线对比。用户判断"更省心"才进入切换。
- **A9 切换后**：
  - `~/.claude/skills` 下没有 devflow-*；
  - settings.json 没有守卫钩子；
  - 新会话 `/dflow` 正常；
  - 任意 Bash 调用没有钩子报错；
  - `./test.sh` 通过。

## 5. 阶段

1. **骨架加验证和五个高频剧本**：入口、授权、原则，以及讲解、排查、方案、实施、验收五个剧本（覆盖历史任务的 70% 左右）；验收剧本带上 create-verification-skill，并为 ludus 生成第一个项目验证技能（pstack："先赢得信任"，不停下等人的前提）；只链接 `dflow`。完成 A1–A5。
2. **其余剧本**：评审、调研、交接、进展、周报、提交与发布、调优。完成 A6、A8。
3. **无人值守**：按决定 9 修订并实现。完成 A7。需要在 ludus 的 r5 收尾后进行演示（不影响 r5 的话可以提前）。
4. **试用**：E1，由用户进行。

## 6. 风险

- **单入口靠用户记得输入 `/dflow`**：试用期可能不习惯。切换阶段在 CLAUDE.md 里加一句指针来缓解；常驻方式（output style、UserPromptSubmit 钩子）未验证，暂不采用。
- **不停下等人会更常出现"做完了但方向不对"**：代价是偶尔回退一批提交。缓解：每个单元单独提交、收尾报告列出所做选择和改回方法；方向性问题仍然停。E1 的纠正统计（尤其 A 通用性、E 偏离目标）用来观察这个代价。
- **全局规则冲突**：`~/.codex/AGENTS.md` 的"偏离原要求的做法由用户决定"和"提交前先确认"与本方案冲突，且全局规则优先于技能。必须由用户修改这两条，否则 dflow 会被拉回停下来问。这是阶段 1 的前置条件。
- **验证能力不足时，不停只会更快地产出没验证的东西**：所以验证技能排在阶段 1。
- **跨模型审查依赖本机 codex**：不可用时一律写"未审查"，不让 Claude 代审。
- **历史数据偏向 GameVistor 项目**：路由表在其他类型项目上可能需要调整。由调优剧本在使用中修正。
- **试用期两套并存**：devflow 技能仍会被自动触发，可能和 dflow 混用。剧本里写明"dflow 会话中不加载 devflow-* 技能"；彻底解决要等切换阶段。
