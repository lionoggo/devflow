# 方案：dflow 第 3 阶段，无人值守剧本

> 状态：待用户批准（第 3 版，两轮 codex 评审均已处理，见第 9 节）。日期 2026-10-14。worktree `devflow-dflow`，分支 `dflow`。
> 上位方案：`docs/plan-dflow.md` 决定 9。
> 底稿：`docs/plan-unattended.md`（为旧 devflow 写的版本），以及 `docs/pstack-analysis/3-long-running.md` 末尾的 14 条修改建议。本文把两者合并，改写成 dflow 剧本。
> pstack 来源：`poteto-mode/playbooks/autonomous-run.md`、`pause-safely.md`、`session-pickup.md`，`show-me-your-work`，`docs/guide/07-overnight.md`。
> 用户已决定（2026-10-14）：
> - 本阶段只支持 Claude Code；
> - 不加 Stop hook，先靠提示词约束；
> - 删除 autorun、guard 和全局钩子放到第 5 阶段切换时，每一步先问；本阶段只新增。

## 1. 结论

新增一个剧本 `playbooks/unattended.md`，配三个小脚本：
- `scripts/log.sh`：决策日志，从 devflow-autorun 复制；
- `scripts/run-state.sh`：运行状态的机械检查（谁在跑、HEAD 对不对、工作区干不干净、是否超时）；
- `scripts/timeline.py`：从对话记录提取命令和结果，给收尾审查用。

运行控制文件只有三个，都在 `.dflow/` 下，不进 Git（另有 `.dflow/tmp/` 放临时文件和证据）：
- `<slug>.md`：运行清单，"开始"时写好，之后不改；
- `<slug>.lease`：当前负责的会话；
- `<slug>.tsv`：决策日志，只追加。

不加运行中的守卫，也不加启动仪式。

**用户的用法：**
1. 说一句"我要去睡了，跑到 <完成条件> 为止"，或"按 docs/plan-x.md 跑完"。
2. 看一屏框定，回复"开始"。
3. dflow 用 `/loop` 自己一轮轮推进，直到完成条件全部通过、到时，或者无路可走。遇到只有用户能定的问题，先做不依赖它的部分；实在没有可做的，才按默认做，单独提交并发通知。
4. 回来时看收尾回复，内容包括：
   - 结果和完成条件的真实输出；
   - 按默认做的决定，每条都能 `git revert`；
   - 收尾检测结果；
   - codex 审查挑出的要点。

**和旧 autorun 比：**
- 去掉了：手写的契约格式校验、`.running` 标记的启动仪式（`arm.sh`）、运行中的守卫。
- 保留了运行定义、负责会话、基线、截止时间、受保护路径这些状态。它们改为"开始"时自动写入运行清单和租约，不需要用户手写。
- 改动受保护文件、推送这类问题，从运行中拦截改为收尾时检测。

## 2. 依据

- **旧 autorun 的实际效果**（ludus 12 次运行，`docs/plan-unattended.md` 2.2 节）：
  - 守卫一次都没拦过东西；
  - 启动仪式失败两次，都是手写标记文件绕过去的；
  - 每次 15–90 分钟就停，用户大约每小时回来一次。推测主要原因是"连续 3 轮无进展就整体收尾"太紧，加上遇到问题就停下等人；没有逐次核实停止原因。
- **pstack 的做法**：
  - 完成条件必须能判对错，时长不算完成条件；
  - 瓶颈期不停，换思路；
  - 可撤销的事不停下等人，只有不可逆的事、实验答不了的偏好问题、真正的死路才停；
  - 每轮记一行决策日志；
  - 暂停和接手有明确步骤。
  - "按默认推进、先绕开继续做"出自 Orchestrate 的 gates（`orchestrate.md:30,105`），autonomous-run 只说"把问题报出来"。
- **信任的前提**：pstack 要求先赢得信任再开循环（`07-overnight.md:9-16`）。第 1、2 阶段证明了短任务的自我验证能力。多小时循环、崩溃恢复和并发接手还没验证，由本阶段的验收和 E1 证明。
- **14 条修改建议**：除第 13 条（Stop hook，用户决定不做）外全部采纳，去向见第 6 节。

## 3. 方案

### 3.1 入口

路由表里"无人值守"一行已经存在（`SKILL.md`），触发语扩充为：
- **开始**："我要离开""去睡了""跑到…为止""别停""无人值守"；
- **接手**："继续无人值守 <slug>"；
- **暂停**："暂停""先停一下""我要重启"。"去睡了""别停"永远不触发暂停。

没有批准过的方案时，完成条件由用户这句话加上框定确定，不要求先走方案剧本。

### 3.2 框定：唯一一次停下

一屏写清以下内容，然后停下等"开始"。这就是 SKILL.md 里"预计超过一小时的任务停一次给出框定"的那一次。

1. **完成条件**：
   - 每条是一个命令加期望结果，附上现在的基线输出；
   - 可以是有序阶段 S1..Sn，每个阶段有自己的条件。有批准方案时，直接取方案里的阶段和验收；
   - 用户只给了时长（"跑 4 小时"），必须补一条能判对错的条件；
   - 如果有比预期实现更便宜、却违背意图的做法也能通过条件，补一条能区分两者的条件；
   - 什么算进展：默认是"一个单元的检查通过，且已完成的条件没有倒退"；非布尔条件（比如失败数、耗时）在这里写明指标。
2. **工作单元**：从方案或目标拆出，风险最高的排前面，标出依赖关系和哪些互相独立。
3. **分支**：工作区干净时，从 HEAD 建本地分支 `dflow/<slug>`；不干净就列出文件并停下，不清理、不暂存。框定获批即授权建这个分支，并在它上面本地提交。
4. **路径范围**：
   - 允许写入的路径：完成任务需要改的目录或文件；
   - 受保护的路径：完成条件用到的测试、样本、脚本，逐个列出，运行中不改。
   - 途中发现需要改范围外的文件，按 3.4 记 `gate` 行、标为卡住。
5. **不会做的事**：
   - push、merge、rebase、reset、stash、clean、cherry-pick、amend；
   - 切换或删除分支、改 tag、动 worktree；
   - 修改受保护的路径；
   - 写外部系统（工单、聊天、发布）。

   本次运行只会向你的设备发两类系统通知（3.6）；"开始"即同意这一项。需要其他任何一项才能继续，就把相关单元标为卡住（3.4）。
6. **已知的待定问题**：框定时就能看出的产品或偏好问题，列出默认值，用户可以当场改。
7. **时长上限**：默认 8 小时，可改。写成绝对截止时间，接手的会话也不会重新获得完整时长。到时后不再开始新的一步；正在做的一步如果已经通过检查，照常提交。
8. **运行环境**：
   - 需要不会弹权限确认的模式，例如 bypassPermissions；
   - Mac 休眠会中断运行，所以会用 `caffeinate`。
9. **首次运行提示**：同类任务第一次无人值守时，建议用户先看前两轮再离开。
10. **怎么启动循环**：框定时先确认 Skill 工具能调用 `loop`。不能时，框定直接给出 `/loop /dflow 继续无人值守 <slug>`，让用户用这一行代替"开始"，不先落状态再等第二次输入。
11. **slug**：只用小写字母、数字和连字符，最长 63 个字符。

**回复"开始"后：**
1. 重新核对 HEAD、工作区和各条件的基线输出。与框定时不一致，就停止启动，重新展示变化。
2. 建分支；确认 `.git/info/exclude` 有 `.dflow/`。
3. 写运行清单 `.dflow/<slug>.md`。开头是固定格式的机器可读段（`slug`、`branch`、`base`、`deadline`、`allow`、`protect`，每行 `键: 值`），后面是给人看的目标、阶段和条件（命令、期望、进展指标）、单元和依赖、已知待定问题和默认值。之后不改；用户明确要求改时，重算哈希并追加 `correction` 行。
4. `run-state.sh claim <slug>`：用 `mkdir` 原子领取，写租约，内容是 `CLAUDE_CODE_SESSION_ID`、`CLAUDE_PID`、清单的 SHA-256 和开始时间。
4. 后台启动 `caffeinate -i -t <到截止时间的秒数>`，把 PID 写进租约。
5. 写 `start` 行，证据列写基线 SHA 和远端引用的摘要。
6. 用 Skill 工具启动 `loop`，不带间隔（动态模式），参数是 `/dflow 继续无人值守 <slug>`。不可用时，请用户自己输入这一行。

### 3.3 每一轮

1. **核对状态**：运行 `run-state.sh check <slug>`。它检查：
   - 租约属于本会话；清单的 SHA-256 与租约记录的一致；
   - 当前分支是 `dflow/<slug>`；
   - HEAD 等于日志里最后一个 `commit <sha>`；
   - 工作区除 `.dflow/` 外是干净的；
   - 没过截止时间。

   每项失败的处理：
   - 租约不属于本会话：停止本会话的循环，不写任何东西。
   - 清单被改过、分支不对：记一行并停下报告，不自己修。
   - HEAD 比日志里最后记录的提交多出恰好一个直接后继提交：多半是上一轮提交后、写日志前中断了。重跑检查，通过就补记一行，不通过就当作没进展的一轮撤销这个提交（`git revert`，不改写历史）。其他不一致都停下报告。
   - 工作区不干净：上一轮正常结束时，一定已经提交或撤销，所以这些改动来源不明，可能是用户、钩子或别的进程留下的。不撤销，不删除。记一行列出文件，停止循环，发通知"受阻：工作区有来源不明的改动"。
   - 过了截止时间：进入收尾。
2. **读状态**：读运行清单和日志最后 15 行。以文件为准，不信记忆。
3. **选下一步**：从未完成、未卡住、未判死路的单元里，选风险最高的那个的最小一步。说出假设。
4. **改动并检查**：跑这一步的检查，加上**所有已完成阶段和当前阶段**的全部条件。
5. **记录结果**（每轮结束前，工作区必须回到干净状态）：
   - **有进展**（按清单里的进展定义，且没有倒退）：`git add <路径>`，本地提交，记一行，证据写 `commit <sha>`。
   - **没有进展，或者有倒退**：只撤销本轮自己编辑过的路径、删掉本轮自己新建的文件，记一行，写明原因和下一步换什么思路。`git status` 里出现本轮没碰过的路径，不动它，按"工作区不干净"停下报告。
   - 提交时只 `git add` 本轮自己编辑过的路径。
6. **途中发现**（`autonomous-run.md` 第 4 条）：
   - 和完成条件相关的工具故障、相关的明显 bug：在范围内用单独提交修，记 `side` 行；
   - 受保护路径里的问题（比如不稳定的检查脚本）：不修，记一行，相关单元标为卡住；
   - 范围外的：写进收尾的"后续事项"，不顺手改。
7. **长时间等待**（长构建、长基准）：用后台 Bash（退出时唤醒）或 Monitor 等事件，不在循环里 sleep 轮询。同时只挂一个等待者。
8. **单元判死路**：
   - 至少两种独立的思路都有明确的失败证据，并且花在这个单元上的时间不少于下限，才记 `dead` 行，转去做别的单元；
   - 时间下限默认 30 分钟，可在框定时改；等待外部构建的时间不算在内。
9. **阶段完成**：当前阶段的条件全部通过，记 `stage-done` 行，进入下一阶段。某阶段卡住时，如果后面的阶段不依赖它，就继续往后做。
10. **停止条件**，以下任一情况进入收尾：
    - 全部完成条件通过；
    - 到了截止时间；
    - 剩余单元全部是死路或卡住，且没有能做的独立单元。

    瓶颈期不停。绝不放宽或重新解释完成条件。

### 3.4 只有用户能定的问题

只指实验无法回答的产品或偏好问题。能用实验回答的，自己做实验。

1. 写 `gate` 行：问题、选项、默认值、理由、用户怎么改。发一次通知。
2. 先做不依赖它的单元。
3. 只有没有独立单元可做时，才按默认推进：
   - 按默认做的提交，信息以 `default:` 开头，方便整段撤销；
   - 同一个默认值上最多再做一个单元，之后把剩余依赖它的单元标为卡住。
4. 需要"不会做的事"才能继续的单元，同样记 `gate` 行、标为卡住，不按默认做。

### 3.5 日志

- 位置 `.dflow/<slug>.tsv`，六列 `ts phase decision why evidence result`。
- `scripts/log.sh` 从 devflow-autorun 复制过来，加一个测试。旧的那份第 5 阶段随 autorun 一起删。
- phase 取值：`start`、`round`、`gate`、`default`、`dead`、`stage-done`、`side`、`blocked`、`pause`、`close`、`correction`。
- 规则照 show-me-your-work：
  - 只追加，记错了就追加 `correction` 行；
  - 记决策点，不记每条命令；
  - 每轮至少一行；
  - 用大白话写给人看，按 `references/unslop.md` 的规则。

### 3.6 通知

用 PushNotification，只在两种时刻发：
- 写了 `gate` 行时："需要你定：<问题>，已先做别的 / 已按默认 <值> 处理"；
- 运行停下时（完成、到时、受阻）："<slug> 完成 / 部分完成 / 受阻"。

发送失败不重试、不影响运行，在收尾回复里提一句。

### 3.7 暂停（只在用户明确说时）

1. 在安全的边界停下：优先做完当前这一步并按 3.3 第 5 步提交，或者撤销它。
2. 只有当前这一步既做不完、撤销又会丢掉有用的半成品时，才把本轮自己的改动做成一个 `wip:` 提交。这是"只提交通过检查的单元"的明确例外。接手后的第一步，必须先验证或撤销这个提交。
3. 写 `pause` 行：当前单元、下一步、要注意的坑。
4. 停止循环；结束 `caffeinate`；释放租约（`run-state.sh release`）。

回复写明：现在在哪、提交了什么、工作区是否干净、恢复后的第一步。

### 3.8 接手（新会话说"继续无人值守 <slug>"）

1. `run-state.sh claim <slug>`：
   - 租约里记录的 `CLAUDE_PID` 还活着：拒绝接手，告诉用户旧会话还在，先关掉它；
   - 进程已不在（或该 PID 现在不是 claude 进程），或租约已释放：改写租约为本会话。
2. 运行 `run-state.sh check <slug>`，处理方式同 3.3 第 1 步。
3. 读运行清单。重跑全部完成条件，不信日志里写的通过。
4. 写 `start` 行，注明接手的 ts 范围和本会话的完整 `CLAUDE_CODE_SESSION_ID`（开始时的 `start` 行同样记录）。截止时间沿用清单里的，不重置。
5. 上一次以 `wip:` 提交结束的，先验证或撤销它。
6. 已提交的单元不重做，从日志和 `git log` 判断下一步。
7. 按剩余时间重启 `caffeinate`，再重启 `/loop`。

### 3.9 收尾

1. 工作区里除 `.dflow/` 外有未提交改动，如实报告，不清理。
2. 在最终提交上重跑全部完成条件，记下真实输出。
3. **对照**：
   - 日志对照 `git log <基线>..HEAD`：每个有进展的行都对应真实提交；
   - 日志对照对话时间线（第 6 步生成）：声称跑过的检查，记录里确实跑过；
   - 不一致就追加 `correction` 行。
4. **收尾检测**（代替运行中的守卫）：
   - `git diff --name-only <基线>..HEAD` 不包含受保护的路径，且全部在允许写入的路径内；
   - 对话时间线里没有 push、reset 等"不会做的事"的命令；
   - 远端引用与 `start` 行记录的对照：写成"未观察到变化 / 有变化"。它不能证明本次运行没有 push（别人也可能推送，推送后也可能被还原），只作为提示。

   结果写进收尾回复。发现问题不自动回滚，交给用户。
5. 写 `close` 行，决定列只写"完成 / 部分完成 / 受阻"之一。
6. **跨模型审查**：
   - 用 `scripts/timeline.py` 从这次运行涉及的所有会话的对话记录生成合并时间线，放到 `scripts/scratch.sh` 的目录。会话 ID 取自日志里所有 `start` 行，对话记录在 `~/.claude/projects/` 下按 ID 定位；找不到的会话列为"未核实"。只提取工具调用的命令和结果，不需要另起子 agent。
   - 把运行清单、日志、`git log -p <基线>..HEAD`、时间线交给 `codex exec -s read-only`，要它列出四类问题：证据薄弱的决定、没有证据就声称通过的验证、事后看有风险的选择、粗看容易漏掉的问题。
   - codex 不可用就写"未审查：<原因>"。
7. 停止循环；用租约里记录的 PID 结束 `caffeinate`，先确认那个 PID 仍是 `caffeinate`；释放租约；发通知。

**收尾回复：**
```text
**结果**：<完成 / 部分完成 / 受阻> — <一句话>
- 完成条件：<每条 → 最终真实输出>
- 提交：<基线..HEAD，n 个；按默认做的单独列出>
- 按默认做的决定：<问题 → 默认值 → 怎么改（git revert <sha>）>
- 卡住和死路：<单元 → 原因 → 需要你做什么>
- 收尾检测：受保护路径 <未改 / 改了哪些>；范围外文件 <无 / 哪些>；危险命令 <无 / 有哪些>；远端 <未观察到变化 / 有变化>
- 后续事项：<范围外发现；没有就省略>
- 影响面：<见 SKILL.md>
- 日志：.dflow/<slug>.tsv（清单 .dflow/<slug>.md）
**需要你注意**（审查：codex / 未审查：原因）
- <审查要点，最多 5 条>
```

### 3.10 脚本

- **`run-state.sh claim|check|release <slug>`**
  - 只读写 `.dflow/<slug>.lease`，并读取日志和 Git 状态，不改其他文件；
  - 输出一行一项的检查结果，退出码 0 表示全部通过；

## 7. 验收

### 环境

- **演示仓库**：新建一个小仓库，包含：
  - 两个有序阶段：S1 实现一个函数，S2 在其上加一个功能；
  - 一个产品偏好问题：问候语用中文还是英文；
  - 一个不依赖该问题的独立单元；
  - 一个本地裸远端。
- **交互会话**：`/loop` 只在交互会话里工作，所以运行类验收在 tmux 里启动交互式 `claude`（bypassPermissions）。用 `tmux send-keys` 发"开始"，用 `tmux capture-pane` 和对话记录取证。
- **摘要**：每项写到 `docs/acceptance/stage3/`，格式同第 2 阶段。

### 实施顺序：先跑通一条最短路径

1. **第一步，最短路径**：框定 → 开始 → 两轮（一轮有进展并提交，一轮无进展并撤销）→ 收尾。先过 A1、A2、A5。
2. **第二步，其余功能**：在第一步通过后，再加多阶段、待定问题、暂停、接手和失败路径（A3、A4、A6–A12）。

### 各项

- **A1 启动**：一句话加一次"开始"，循环自动启动，之后不再需要输入。`.dflow/` 下的控制文件只有清单、租约和日志（另有 `tmp/`）。证据：tmux 画面、对话记录里的 Skill 调用、`.dflow/` 目录。
- **A2 日志与提交一致**：每个有进展的行都对应真实提交；没进展的改动被撤销，每轮结束时工作区干净。证据：日志对照 `git log`，`git status`。
- **A3 先做独立单元**：遇到问候语问题时，写了 `gate` 行、发了通知，先做独立单元；只有没有独立单元时才按默认推进，相关提交以 `default:` 开头；运行一直跑到结束，中途没有停下等人。
- **A4 多阶段且不倒退**：
  - S1 通过后写 `stage-done`，继续做 S2，同一分支顺序提交；
  - 在 S2 里预置一个容易想到、但会破坏 S1 的做法（例如改动 S1 的函数签名）。这样的提交不能被接受：要么没提交，要么在同一轮被撤销。
- **A5 收尾**：回复包含：
  - 完成条件的真实输出、提交范围；
  - 按默认做的决定和撤销方法；
  - 三项收尾检测的结果；
  - 第一行写明审查模型的"需要你注意"段。

  同时核对：`git diff <基线> -- <受保护路径>` 为空；`caffeinate` 已结束；租约已释放。
- **A6 中途杀掉后接手**：
  - 运行到 S1 完成、S2 未完成时，杀掉 tmux 会话。
  - 新会话说"/dflow 继续无人值守 <slug>"后：写了带继承范围的 `start` 行；重跑了完成条件；截止时间没重置；没有重做已提交的单元；一直跑到结束。
  - 收尾的时间线同时包含前后两个会话。
- **A7 暂停**：
  - 运行中发"暂停"：有 `pause` 行；循环停止；`caffeinate` 结束；只有在做不完、又不能撤销的情况下才出现 `wip:` 提交。
  - 另用"我去睡了，别停"开一次运行，确认不触发暂停。
- **A8 收尾检测能发现问题**：在运行分支上手工追加一个改了受保护测试文件的提交，同时追加一行对应的日志，让 HEAD 核对能通过。再让会话收尾，收尾回复必须报告这个文件被改过。
- **A9 来源不明的改动**：运行中强杀会话，再从另一个进程往仓库里写一个文件。接手时必须停下报告这个文件，不能删除或撤销它。
- **A10 拒绝第二个负责会话**：旧会话的循环还活着时，在另一个会话里说"继续无人值守 <slug>"，必须拒绝接手。
- **A11 提前完成和到时**：
  - 一次运行提前完成：`caffeinate` 被结束，结束的是本次运行启动的那一个，其他 `caffeinate` 进程不受影响；
  - 一次运行把截止时间设为 5 分钟：到时进入收尾，报告"部分完成"。
- **A12 审查和通知不可用**：临时让 `codex` 命令不可用（在 PATH 前放一个直接失败的同名脚本），收尾写"未审查：原因"，其余部分正常完成。
- **A13 范围外改动**：在运行分支上手工追加一个改了允许范围外文件的提交（同时补一行日志），收尾必须报告它。
- **脚本测试**：除常规用例外，`run-state-test.sh` 覆盖：两个进程同时 `claim` 只有一个成功；租约里的 PID 已被别的进程占用时可以接手；非法 slug 被拒绝；清单被改后 `check` 失败；恰好多一个未记录提交时识别出来。
- **原有的脚本测试**：`log-test.sh`、`run-state-test.sh`、`timeline-test.sh` 通过，并入 `./test.sh`。

**E1 真实试用**（上位方案第 4 阶段，由用户进行）：在 ludus 用无人值守跑一个多阶段任务，记录：
- 是否完成；
- 用户介入次数和阶段数，与旧 autorun"约每小时一次"对比。

## 8. 风险

- **没有结构性守卫**：模型不守规矩时，push 或改测试都不会被拦，只能在收尾时被检测到（A8）。推送这种不可逆的事，检测只能事后发现。
- **动态 `/loop` 依赖会话存活**：会话被关闭，或机器休眠超时，循环就停。靠接手（3.8）续跑。
- **按默认做可能被滥用**：模型可能把该停下的事当成默认推进。缓解：`default:` 单独提交、同一默认值上最多叠一个单元、收尾清单、codex 审查。
- **同一文件被外部同时修改**：撤销只针对本轮编辑过的路径，但如果用户在同一轮里改了同一个文件，撤销仍会覆盖用户的改动。按文件哈希核对可以避免，但这种情况很少，暂不做；无人值守期间请不要在同一仓库里手动改文件（框定里写明）。
- **工作区不干净就停**：这条规则安全，但会让崩溃后的运行停下等人。崩溃本来就少见，用丢数据的风险换不停下不划算。
- **验收在小仓库里进行**：多阶段、长等待、真实基准只有在 ludus 上才能暴露，所以要靠 E1。
- **两套并存**：第 5 阶段前，旧 autorun 仍可用。dflow 会话里规定不加载 devflow-* 技能。

第二轮评审（第 2 版）结论"修改后执行"：1 条 P0、5 条 P1、4 条 P2。按"最多两轮"的规则，不再做第三轮，处理如下：

| 意见 | 处理 |
|---|---|
| P0 轮中有外部改动时撤销会覆盖它 | 部分采纳：只撤销、只提交本轮自己编辑过的路径，出现本轮没碰过的路径就停下。同一文件被同时修改的情况不做哈希核对，列入风险，并在框定里提醒用户不要同时手动修改（成本与概率不相称） |
| P1 清单没有机器可读格式和完整性校验 | 采纳：清单开头加固定的 `键: 值` 段，租约记清单哈希，每轮核对 |

| P1 没有允许写入范围 | 采纳：清单加允许写入路径，收尾检查；增加 A13 |
| P2 循环能力到"开始"后才检查 | 采纳：框定时确认，不能自动启动就让用户用 `/loop` 那一行代替"开始" |

| P2 "开始"时没有重新核对 | 采纳：开始后先重新核对 HEAD、工作区和基线 |
