# 方案：dflow 第 3 阶段，无人值守剧本

> 状态：待用户批准（第 1 版）。日期 2026-10-14。worktree `devflow-dflow`，分支 `dflow`。
> 上位方案：`docs/plan-dflow.md` 决定 9。
> 底稿：`docs/plan-unattended.md`（为旧 devflow 写的版本），以及 `docs/pstack-analysis/3-long-running.md` 末尾的 14 条修改建议。本文把两者合并，改写成 dflow 剧本。
> pstack 来源：`poteto-mode/playbooks/autonomous-run.md`、`pause-safely.md`、`session-pickup.md`，`show-me-your-work`，`docs/guide/07-overnight.md`。
> 用户已决定（2026-10-14）：
> - 本阶段只支持 Claude Code；
> - 不加 Stop hook，先靠提示词约束；
> - 删除 autorun、guard 和全局钩子放到第 5 阶段切换时，每一步先问；本阶段只新增。

## 1. 结论

新增一个剧本 `playbooks/unattended.md` 和一个日志脚本 `scripts/log.sh`（从 devflow-autorun 复制）。不新增其他机制。

用户的用法：
1. 说一句"我要去睡了，跑到 <完成条件> 为止"（或"按 docs/plan-x.md 跑完"）。
2. 看一屏框定，回复"开始"。
3. dflow 用 `/loop` 自己一轮轮推进，直到完成条件全部通过或真正无路可走。遇到只有用户能定的问题，先做不依赖它的部分，实在没有才按默认做，并单独提交、发通知。
4. 回来时看收尾回复：结果、完成条件的真实输出、按默认做的决定（每条可以 `git revert`）、codex 审查挑出的要点。

和旧 autorun 相比，去掉了契约文件、`.running` 标记、`arm.sh`、`check.sh`、运行中的守卫；保留了两件真正有用的事：每轮开头核对 HEAD 和日志一致，以及决策日志。改动受保护文件这类问题，从"运行中拦截"改为"收尾时检测"。

## 2. 依据

- **旧 autorun 的实际效果**（ludus 12 次运行，`docs/plan-unattended.md` 2.2 节）：
  - 守卫一次都没拦过东西；
  - 启动仪式失败两次，都是手写标记文件绕过去的；
  - 每次 15–90 分钟就停，用户大约每小时回来一次。主要原因是"连续 3 轮无进展就整体收尾"太紧，加上所有问题都停下等人。
- **pstack 的做法**：
  - 完成条件必须能判对错，时长不算完成条件；
  - 瓶颈期不停，换思路；
  - 可撤销的事不停下等人，只有不可逆、无法用实验回答的偏好问题、真正的死路才停；
  - 每轮记一行决策日志；
  - 暂停和接手各有明确步骤；
  - 先赢得信任再开循环（`07-overnight.md:9-16`）。dflow 第 1、2 阶段的验证技能和验收就是为此准备的。
- **14 条修改建议**：全部采纳，第 13 条（Stop hook）按用户决定不做。对应关系见第 6 节。

## 3. 方案

### 3.1 入口

路由表里"无人值守"一行已经存在（`SKILL.md`），触发语扩充为：
- 开始："我要离开""去睡了""跑到…为止""别停""无人值守"；
- 接手："继续无人值守 <slug>"；
- 暂停："暂停""先停一下""我要重启"。"去睡了""别停"永远不触发暂停。

没有批准过的方案时，完成条件由用户这句话加框定确定，不要求先走方案剧本。

### 3.2 框定：唯一一次停下

一屏写清以下内容，然后停下等"开始"。这是 SKILL.md 里"预计超过一小时的任务停一次给出框定"的那一次。

1. **完成条件**：
   - 每条是一个命令加期望结果，附现在的基线输出；
   - 可以是有序阶段 S1..Sn，每个阶段有自己的条件。有批准方案时，直接取方案里的阶段和验收；
   - 用户只给了时长（"跑 4 小时"），必须补一条能判对错的条件；
   - 如果有比预期实现更便宜、却违背意图的做法也能通过条件，补一条能区分两者的条件。
2. **工作单元**：从方案或目标拆出，风险最高的排前面，标出哪些互相独立。
3. **分支**：工作区干净时，从 HEAD 建本地分支 `dflow/<slug>`；不干净就列出文件并停下，不清理、不暂存。框定获批即授权建这个分支，并在它上面本地提交。
4. **受保护的路径**：完成条件用到的测试、样本、脚本，逐个列出。运行中不改它们。
5. **不会做的事**：
   - push、merge、rebase、reset、stash、clean、cherry-pick、amend；
   - 切换或删除分支、改 tag、动 worktree；
   - 修改受保护的路径；
   - 对外发送或发布任何东西。

   需要其中任何一项才能继续，就把相关单元标为卡住（3.4）。
6. **已知的待定问题**：框定时就能看出的产品或偏好问题，列出默认值，让用户可以当场改。
7. **时长上限**：默认 8 小时。
8. **运行环境**：需要不会弹权限确认的模式（例如 bypassPermissions）；Mac 休眠会中断运行，所以会用 `caffeinate`。
9. **首次运行提示**：同类任务第一次无人值守时，建议用户先看前两轮再离开。

回复"开始"后：
1. 建分支；确认 `.git/info/exclude` 有 `.dflow/`。
2. 写 `start` 行，证据列记下基线 SHA 和远端引用的摘要（`git ls-remote` 或本地 `show-ref` 的哈希），供收尾对照。
3. `caffeinate -i -t <上限秒数>` 放到后台。
4. 用 Skill 工具启动 `loop`，不带间隔（动态模式），参数是 `/dflow 继续无人值守 <slug>`。不可用时，请用户自己输入这一行。

### 3.3 每一轮

1. **收敛**（每轮开头，保证重复执行也安全）：
   - 读日志最后 15 行和完成条件。以文件为准，不信记忆。
   - 看 `git status`。有未提交改动，说明上一轮中断了：最后一行是"进行中"就重跑检查，按有无进展处理；否则撤销。记一行。
   - 核对 HEAD 等于日志里最后一个 `commit <sha>`。不等就记一行并停下报告，不自己修。
2. **选下一步**：从未完成、未卡住、未判死路的单元里，选风险最高的那个的最小一步。说出假设。
3. **改动并检查**：跑这一步的检查，加上当前阶段的全部完成条件。
4. **记录结果**：
   - 有进展（某个条件更接近通过，且没有倒退）：`git add <路径>`，本地提交，记一行，证据写 `commit <sha>`。
   - 没有进展：撤销本轮自己的改动，删掉本轮新建的文件，记一行，写明原因和下一步换什么思路。
5. **途中发现**（`autonomous-run.md` 第 4 条）：
   - 和完成条件相关的工具故障、相关的明显 bug：在范围内用单独提交修，记一行；
   - 受保护路径里的问题（比如不稳定的检查脚本）：不修，记一行，相关单元标为卡住；
   - 范围外的：写进收尾的"后续事项"，不顺手改。
6. **长时间等待**（长构建、长基准）：用后台 Bash（退出时唤醒）或 Monitor 等事件，不在循环里 sleep 轮询。同时只挂一个等待者。
7. **单元判死路**：一个单元至少换过两种不同思路、耗时超过 30 分钟仍无进展，记 `dead` 行，转去做别的单元。
8. **阶段完成**：当前阶段的条件全部通过，记 `stage-done` 行，进入下一阶段。某阶段卡住时，如果后面的阶段不依赖它，就继续往后做。
9. **停止条件**：
   - 全部完成条件通过：进入收尾；
   - 到达时长上限：进入收尾；
   - 剩余单元全部是死路或卡住，且没有能做的独立单元：进入收尾。

   瓶颈期不停。绝不放宽或重新解释完成条件。

### 3.4 只有用户能定的问题

只指实验无法回答的产品或偏好问题。能用实验回答的，自己做实验。

1. 写 `gate` 行：问题、选项、默认值、理由、用户怎么改。发一次通知。
2. 先做不依赖它的单元。
3. 只有没有独立单元可做时，才按默认推进。按默认做的提交，信息以 `default:` 开头，方便整段撤销。不在默认值上越叠越多：同一个默认值上最多再做一个单元，之后把剩余依赖它的单元标为卡住。
4. 需要"不会做的事"才能继续的单元，同样记 `gate` 行、标为卡住，不按默认做。

### 3.5 日志

- 位置 `.dflow/<slug>.tsv`，六列 `ts phase decision why evidence result`。
- `scripts/log.sh` 从 devflow-autorun 复制过来，加一个测试 `scripts/log-test.sh`。旧的那份第 5 阶段随 autorun 一起删。
- phase 取值：`start`、`round`、`gate`、`default`、`dead`、`stage-done`、`side`、`pause`、`close`、`correction`。
- 规则照 show-me-your-work：
  - 只追加，记错了就追加 `correction` 行；
  - 记决策点，不记每条命令；
  - 每轮至少一行；
  - 用大白话写给人看，按 `references/unslop.md` 的规则。

### 3.6 通知

用 PushNotification，只在两种时刻发：
- 写了 `gate` 行时："需要你定：<问题>，已先做别的 / 已按默认 <值> 处理"；
- 运行结束时："<slug> 完成 / 部分完成 / 受阻"。

发送失败不重试，也不记日志。

### 3.7 暂停（只在用户明确说时）

1. 在安全的边界停下：做完或撤回当前这一步，不开新单元。
2. 未提交的改动做成一个 `wip:` 提交。
3. 写 `pause` 行：当前单元、下一步、要注意的坑。
4. 停止循环（不再安排下一次唤醒）。

回复写明：现在在哪、提交了什么、工作区是否干净、恢复后的第一步。

### 3.8 接手（新会话说"继续无人值守 <slug>"）

1. 确认当前分支是 `dflow/<slug>`，HEAD 等于日志里最后记录的提交。不一致就停下报告。
2. 重跑全部完成条件，不信日志里写的通过。
3. 写 `start` 行，注明接手的 ts 范围。
4. 已提交的单元不重做。从日志和 `git log` 判断下一步。
5. 重启 `/loop`。

### 3.9 收尾

1. 工作区里除 `.dflow/` 外有未提交改动，如实报告，不清理。
2. 在最终提交上重跑全部完成条件，记下真实输出。
3. **对照**：
   - 日志对照 `git log <基线>..HEAD`：每个有进展的行都对应真实提交；
   - 日志对照本会话的对话记录：声称跑过的检查，记录里确实跑过；
   - 不一致就追加 `correction` 行。
4. **结构化检测**（代替运行中的守卫）：
   - `git diff --name-only <基线>..HEAD` 不包含受保护的路径；
   - 远端引用与 `start` 行记录的一致；
   - 结果写进收尾回复。发现问题不自动回滚，交给用户。
5. 写 `close` 行，决定列只写"完成 / 部分完成 / 受阻"之一。
6. **跨模型审查**：
   - 先让一个 Claude 子 agent 把本会话的对话记录（`~/.claude/projects/...` 下的 jsonl）压成"时间、动作、验证命令和结果"的时间线文件，放到 `scripts/scratch.sh` 的目录；
   - 再把日志、`git log -p <基线>..HEAD`、完成条件和时间线交给 `codex exec -s read-only`，要它列出证据薄弱的决定、没有证据就声称通过的验证、事后看有风险的选择、粗看容易漏掉的问题。
   - codex 不可用就写"未审查：<原因>"。
7. 停止循环，杀掉 `caffeinate`，发通知。

**收尾回复**：
```text
**结果**：<完成 / 部分完成 / 受阻> — <一句话>
- 完成条件：<每条 → 最终真实输出>
- 提交：<基线..HEAD，n 个；按默认做的单独列出>
- 按默认做的决定：<问题 → 默认值 → 怎么改（git revert <sha>）>
- 卡住和死路：<单元 → 原因 → 需要你做什么>
- 检测：受保护路径 <未改 / 改了哪些>；远端 <未变 / 变了>
- 后续事项：<范围外发现；没有就省略>
- 影响面：<见 SKILL.md>
- 日志：.dflow/<slug>.tsv
**需要你注意**（审查：codex / 未审查：原因）
- <审查要点，最多 5 条>
```

### 3.10 与其他剧本的关系

- 进展剧本已经读 `.dflow/*.tsv`，运行中问"进展"可以直接用。
- 方案剧本产出的阶段和验收，可以直接作为完成条件。
- 实施剧本的规则在每一轮里照常适用：单元小步、改约定时做影响面分析、迁完调用方。

## 7. 验收

**环境**：
- 演示仓库：新建一个小仓库，含两个有序阶段（S1 实现一个函数、S2 在其上加一个功能），一个产品偏好问题（问候语用中文还是英文），以及一个不依赖该问题的独立单元。配一个本地裸远端。
- 交互会话：`/loop` 只在交互会话里工作，所以 A1–A5 在 tmux 里启动交互式 `claude`（bypassPermissions），用 `tmux send-keys` 发"开始"，`tmux capture-pane` 和对话记录取证。
- 每项摘要写到 `docs/acceptance/stage3/`，格式同第 2 阶段。

**各项**：
- **A1 启动**：一句话加一次"开始"，循环自动启动，之后不需要再输入。没有用到契约文件、`.running`、`arm.sh`。证据：tmux 画面、对话记录里的 Skill 调用、`.dflow/` 目录内容。
- **A2 日志与提交一致**：每个有进展的行对应真实提交；没进展的改动被撤销，工作区干净。证据：日志对照 `git log`，`git status`。
- **A3 先做独立单元**：遇到问候语问题时写了 `gate` 行、发了通知，先做独立单元；只有在没有独立单元时才按默认推进，相关提交以 `default:` 开头；运行一直跑到结束，中途没有停下等人。
- **A4 多阶段**：S1 通过后写 `stage-done`，继续做 S2，同一分支顺序提交。
- **A5 收尾**：回复含完成条件真实输出、提交范围、按默认做的决定和撤销方法、受保护路径和远端的检测结果，以及第一行写明审查模型的"需要你注意"段。远端引用不变，`git diff <基线> -- <受保护路径>` 为空。
- **A6 中途杀掉后接手**：运行到 S1 完成、S2 未完成时杀掉 tmux 会话。新会话说"/dflow 继续无人值守 <slug>"：写了带继承范围的 `start` 行，重跑了完成条件，没有重做已提交的单元，跑到结束。
- **A7 暂停**：运行中发"暂停"：有 `wip:` 提交（或工作区本来就干净）和 `pause` 行，循环停止。另用"我去睡了，别停"开一次运行，确认不会触发暂停。
- **A8 收尾检测能发现问题**：在一次运行的分支上手工追加一个改了受保护测试文件的提交，再让会话收尾。收尾回复必须报告这个文件被改过。

**E1 真实试用**（属于上位方案的第 4 阶段，由用户进行）：在 ludus 用无人值守跑一个多阶段任务。记录完成情况、用户介入次数与阶段数，与旧 autorun"约每小时一次"对比。

## 8. 风险

- **没有结构性守卫**：模型不守规矩时，push 或改测试都不会被拦，只能在收尾时被检测到（A8）。远端被推送这种不可逆的事，检测只能事后发现。
- **动态 `/loop` 依赖会话存活**：会话被关闭或机器休眠超时，循环就停。靠接手（3.8）续跑。
- **按默认做可能被滥用**：模型可能把该停的事当成默认推进。缓解：`default:` 单独提交、同一默认值上最多叠一个单元、收尾清单和 codex 审查。
- **验收在小仓库里进行**：多阶段、长等待、真实基准在 ludus 才能暴露，所以要靠 E1。
- **两套并存**：第 5 阶段前，旧 autorun 仍可用；dflow 会话里规定不加载 devflow-* 技能。
