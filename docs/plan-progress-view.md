## 第一部分：进展页核心

**目标**：在用 devflow-plan 定方案、再拆成多份 autorun 契约实施的任何项目里，一个本地页面就能看到：
- 当前阶段；
- 每份计划契约及其各次运行的状态和花费；
- 哪个运行正在跑、最后一次更新是什么时候；
- 等用户处理的决策和人工项，用户处理后能看到结果。

离开终端用浏览器也能看。运行进入终态、出现新的待决策事项时，主动通知。

**非目标**：
- 不改 `.tsv` 的列格式，也不改 `log.sh`；
- 不替代 devflow-report；
- 不做云端或手机页面（手机上只收通知）；
- 不覆盖 Codex；
- 不处理派发回执，也不处理武装步骤被跳过；
- 不解析契约正文的自由文本来推断状态；
- 第一部分不包含审查标记和对账问题，这两类在第三部分接入。

### 决定

**1. 方案登记表 `.devflow/roadmap.json`**

每个项目一份，不进 git。它是本机的映射，不是方案本身。

```json
{
  "version": 1,
  "stages": [
    {"id": "P1", "title": "最小可玩闭环", "plan": "docs/plans/p1-plan.md", "plan_sha256": "…",
     "contracts": [{"id": "p1-godot", "title": "Godot 引擎", "runs": ["p1-godot", "p1-godot-r2", "p1-godot-r3"]}]}
  ],
  "checks": [
    {"id": "P1/H6", "text": "技能正文质量通读", "source": "docs/plans/p1-plan.md §6"},
    {"id": "p1-godot-r3/B7抽查", "text": "…", "source": ".devflow/p1-godot-r3.md 人工项"}
  ]
}
```

- **`runs` 数组的顺序就是重试顺序，以它为准。** "最后一次运行"指数组最后一个元素，不按文件名、修改时间或字典序判断。
- **登记错误**：同一个运行出现两次、同一个运行挂在两份计划契约下、登记的运行在 `.devflow/` 里找不到契约文件，都在页面顶部显示为"登记错误"，不猜测。
- **人工项编号带命名空间**：计划级用 `<阶段>/<编号>`，契约级用 `<运行>/<编号>`。
- **谁来写**：只由 devflow-autorun 在武装和续跑时写，这两个时刻用户都在场。写入通过 `status.py <root> register <slug>` 完成，不再让模型手写 `jq` 命令：
  - 它只读契约里的严格字段（见第 10 条）：`阶段`、`计划契约`、`花费`、人工项行，再加上计划文件里那张人工项表。按固定前缀逐行匹配，不解析其他自由文本。缺少 `阶段` 或 `计划契约` 字段就报错退出，不靠名字猜。
  - 运行编号就是契约的 slug。它会被追加到对应计划契约 `runs` 的末尾；已经在里面的不重复追加。对应的计划契约不存在就新建。
  - 人工项按编号更新或新增。同一编号已经登记、但内容不同的，报登记错误，不覆盖。
  - 花费命令和上限从契约登记到这个运行名下，同时更新 `plan_sha256`。
  - 先用 `register --dry-run` 输出改动和当前登记表的 sha256，展示给用户；用户同意后，再用 `register --apply --expect <sha256>` 写入。
- **写入时的并发保护**：`--apply` 在 `status.lock` 锁内（见第 6 条）重新计算登记表的 sha256，和 `--expect` 不一致就拒绝写入，要求重新 dry-run，这样不会覆盖别的会话的修改。写入用"写临时文件再 `mv`"的方式完成。
- **同步提示**：计划文件的哈希和 `plan_sha256` 不一致时，在该阶段上显示"登记待同步"。
- **未挂接的运行**：`.devflow/` 里首行以 `# 自动运行契约：` 开头、但登记表里找不到的运行，放在"未挂接的运行"分组里显示。
- **`status.py` 读什么**：平时生成页面只读登记表、日志、运行标记、作业文件和对账文件，外加契约的首行，用来判断这个文件是不是契约。花费命令也从登记表读取，不再去解析契约正文。

**2. 状态推导**

`status.py` 只读取来源文件，自己不维护状态。

**运行的状态：**

| 条件 | 状态 |
|---|---|
| 有运行标记 | 运行中，同时显示最后一条日志的时间。超过 45 分钟没有新日志，显示"运行中·可能失联" |
| 有 `phase=close` 的行 | 取最后一条 `close` 行的 **decision 列**：去掉 `log.sh` 可能加的开头单引号，按空白或"—"切分后取第一个词，必须是"完成""部分完成""受阻"之一，否则显示"解析错误" |
| 有日志，但没有 `close` 行，也没有运行标记 | 未收尾 |
| 只有契约文件 | 起草中 |

- **"已运行"的定义**：有 TSV 或运行标记。只有 `.md` 的运行不算已运行。
- **完成条件的最新状态**：取最后一条 phase 不属于 `start`、`close`、`review` 的日志行的 result 列。收尾后改为显示 `close` 行的 result 列。

**计划契约的状态：**
- 没有任何已运行的运行 → 未开始；
- 任一运行在跑 → 运行中；
- 否则取 `runs` 中最后一个已运行的运行的状态。

**阶段的状态：**
- `plan` 为空，或者没有挂任何契约 → 未开始；
- 所有计划契约都是"完成" → 完成；
- 有任何已运行的运行 → 进行中；
- 否则 → 未开始。

**3. "等你处理"队列**

第一部分只包含两类事项：

| 类型 | 来源 | 编号 |
|---|---|---|
| 决策 | 日志中 decision 列或 result 列含 `parked:` 的行，每行算一条 | `<运行>/D<n>`，n 为该日志里第几条这样的行。日志只追加，所以编号稳定 |
| 人工项 | 登记表的 `checks` | 登记时的编号 |

旧的停放事项，只要没有用户的答复记录，就一直显示"待决定"，不从后续契约的正文里推测"已经解决"。

**4. 写回答复**

答复写到方案级日志 `.devflow/roadmap.tsv`，沿用 `log.sh` 的六列格式。

- **行格式**：phase = `user`；decision = `<事项编号> <动作>`；why = 答复内容；evidence 可选；result 留空。动作有四种：
  - 已处理：人工项做完了；
  - 已决定：决策有了结论。只表示有结论，不表示已经实施，实施由后续契约负责；
  - 已查看：留给第三部分使用；
  - 撤回：撤销之前的答复。
- 同一个编号以最后一行为准。撤回后，事项回到未处理。
- 页面上逐项作答后，点"生成答复"，得到两样东西：
  - 一句话，例如"P1/H6 已处理；p1-bench/D1 已决定：改夹具"；
  - 对应的 `log.sh` 命令，单引号已转义。

  你可以把这句话交给任意 Claude 会话执行，也可以用 `!` 直接运行命令。
- 读取 `roadmap.tsv` 时跳过重复的表头行。追加写入不加锁。

**5. 花费**

- 契约模板新增一行可选字段：`- 花费：命令 \`<cmd>\`；上限 $<n>`，命令和上限都可以省略。
- **口径**：命令输出本次运行到目前为止的累计美元数。具体包括哪些调用，由契约作者写明，并在武装时交给用户确认。命令应当只读，不调用模型或网络。
- **执行**：`status.py` 从登记表取出命令，在仓库根目录执行，限时 10 秒。
  - 没写命令 → 显示"未统计"；
  - 出错、超时或输出不是数字 → 显示"读取失败"，不显示 0。
- **缓存**：已收尾的运行，用（运行名、契约 sha256、`close` 行时间）作为缓存键，缓存在 `status.json` 里。缓存键不变就不再执行命令；旧的 `status.json` 不存在或损坏时重新计算。
- **汇总**：计划契约汇总它所有运行的花费，阶段和整个方案再逐级汇总。只要有一项未知，就显示为"至少 $X（部分未统计）"。

**6. 生成物和通知进度**

页面快照和通知进度是两件事，分开存放：

- **一把锁管整次运行**：`status.py` 的每一种运行方式（普通刷新、`--notify`、`register`）一开始就用 `fcntl.flock` 对 `.devflow/status.lock` 加排他锁，读取来源、计算、写文件全部在锁内完成，结束时才释放。所以多次运行一定是一个接一个、按时间顺序提交的，晚开始的运行不会用旧状态覆盖新状态。一次运行通常只要几秒，排队的代价可以忽略。每条花费命令限时 10 秒；已收尾的运行用缓存，不重复执行，所以只有运行中、或者缓存失效的运行会执行花费命令，一次刷新的最长耗时约为"这类运行的个数 × 10 秒"。
- **页面快照**：计算当前状态，生成 `.devflow/status.json` 和自包含的 `.devflow/status.html`，都先写临时文件再原子替换。`status.json` 只是给页面用的当前状态，不参与通知判断。不带 `--notify` 的运行只做这一件事。
- **通知进度 `.devflow/notify-state.json`**：记录"已经通知过的业务状态"，内容是每个运行的状态，以及已通知过的待决策事项编号集合。只有 `status.py <root> --notify` 会读写它。
  - `--notify` 的步骤：在同一把锁内生成页面快照，然后读取通知进度、计算待通知事件、原子写入新的通知进度，释放锁后把事件以 JSON 输出到标准输出。
  - 事件只有两种：某个运行进入"完成""部分完成""受阻"之一；新增了待决策事项（第三部分再加审查标记）。
  - 没有通知进度文件，或者文件无法解析 → 把当前状态记为基线，不输出事件。
  - 事件在输出时就算已经消费。调用方之后发送通知时即使返回"未发送"，也不重试，避免每轮重复推送；页面始终显示当前状态，不会因为通知没送达而丢失信息。
  - 因为整次运行都在锁内，同一个事件只会被一个调用方拿到，通知进度也不会被改回较旧的状态。

**7. 页面**

- **顶部一行**：方案状态 · 计划契约完成数 · 花费 · 等你处理：N 决策 · M 人工项 · 正在运行：… · 生成于 <时间>。如果有登记错误，在下面单独列出。
- **待处理队列**：带编号，可以逐项作答。有"生成答复"和"复制"按钮；剪贴板不可用时，退回为选中文本让你手动复制。
- **阶段树**：用 `<details>` 默认折叠，层级是阶段 → 计划契约 → 运行。展开某次运行，能看到完成条件的最新状态、关键事件（start、停放、撤回、受阻、close）和证据指针。
- **刷新**：JS 每 60 秒重新加载一次；只要你开始作答，就暂停自动刷新。
- **安全**：所有来自来源文件的文本都做 HTML 转义；页面不引用任何外部资源。

**8. 刷新时机**

- tick 每次运行 `log.sh` 之后、收尾结束时，都用 `--notify` 方式运行；
- autorun 武装、续跑并更新登记表之后；
- 随时手动运行：`python3 -I ~/.agents/skills/devflow-autorun/scripts/status.py <root>`。

**9. 通知**

- **谁来发**：tick（以及第二部分里处理审查结果的会话）运行 `status.py <root> --notify`。有事件就调用一次 PushNotification，同一次调用拿到的多个事件合并成一条，不超过 200 个字符，开头先说你要做什么。其他时候运行 `status.py` 不带 `--notify`。
- **"未收尾"不主动通知**：进程崩溃时没有 tick 来发通知，下次刷新时会在页面上显示。
- 通知的发送结果不写进日志。

**10. 模板**

- `devflow-plan/references/plan.md` 加一段：计划要拆成多份契约时，写明阶段编号、每份契约的名称，以及一张人工项表（`| 编号 | 内容 | 方法 |`）。
- `devflow-autorun/references/contract.md` 新增以下严格字段，每个字段占一行，前缀固定：
  - `- 阶段：<阶段编号>`（必填）；
  - `- 计划契约：<计划契约编号>`（必填）。重试时沿用原来的编号，比如 `p1-godot-r2` 也写 `p1-godot`；
  - `- 花费：命令 \`<cmd>\`；上限 $<n>`（可选）；
  - 人工项一行一条，格式为 `- <编号>：<内容>`，写在"人工项"字段下面。
- 新字段只对新契约生效；旧契约要挂接，就在登记表里手工补登（B1 就是这样做的）。

**11. 进展查询**

不想开网页时，可以直接问。`/devflow-autorun 进展` 会运行 `status.py <root> --summary`（不带 `--notify`，不消费通知），在对话里用几行话汇报：
- 方案状态；
- 正在跑什么；
- 最近一次收尾的结果；
- 等你处理的事项数量，以及前几条的编号；
- 页面路径。

这一条借鉴自 pstack 的 `catch me up`。

**12. 归属**

`status.py` 放在 `devflow-autorun/scripts/`。它和 devflow-report 互不依赖；devflow-report 以后可以读 `status.json`。

## 第二部分：autorun 日志修订和收尾后的审查

**目标**：
- 日志不再作为运行授权、安全拦截或 `check.sh` 是否通过的依据。它仍然是页面展示、通知和事后审计的输入，以给人读为准来写；
- 收尾时，拿日志对照 transcript 自查，再和 git 对账；
- 收尾之后，由另一个模型家族（codex）审查收尾时的提交。审查不阻塞收尾。审查结果无论会话是否还在，都会保存到文件，页面上能看到；会话还在时，再主动补发 Attention 并通知。

**非目标**：不改 `log.sh`、`guard.sh`、表头；不处理武装步骤被跳过。

### 决定

**1. `check.sh` 的两处修改**

- **不再读日志**：删掉"HEAD 必须等于日志里最后一个 commit"这条检查，保留合同哈希、分支、base 是 HEAD 的祖先、`base..HEAD` 和工作区的范围检查、收尾时的未提交检查。
  代价（用户已接受）：运行期间如果有人在同一分支的写入范围内追加提交，不会立即停下，要到收尾对账时才报出来。另外 `git diff base HEAD` 只看净差异，"改过受保护文件后又改回来"抓不到，这是原有限制。这两点都写进 autorun 的 SKILL.md。
- **修复截止时间判断**：截止时间已过，在普通 tick 中仍然算问题，要求停下并收尾；在 `closeout` 模式下不算问题，因为截止时间到了本来就是进入收尾的正常原因。这是现有的 bug。

**2. `reconcile.sh <root> <slug> [base]`**

只报告问题，不让运行停下。

- **输出格式**：首行 `meta\tbase <sha>\thead <sha>`；之后每个问题一行，格式为 `issue\t<kind>\t<sha或->\t<说明>`。没有问题时只输出 meta 行，退出码 0；有问题时退出码 1。
- **问题种类 `kind`**：
  - `unlogged`：有提交，但日志里没有对应行；
  - `out_of_range`：日志里写的 commit 不在 `base..HEAD` 范围内；
  - `unresolved`：日志里的 SHA 解析不出来，或者有歧义。
- **读取规则**：
  - 提取 SHA 时要求完整的词边界：`commit ([0-9a-f]{7,40})` 后面必须紧跟非字母数字字符或行尾；
  - 每个 SHA 用 `git rev-parse --verify --quiet <sha>^{commit}` 解析；
  - base 无效、`rev-list` 失败或日志不可读时，退出码为 2，并且不输出任何 `issue` 行；
  - 历史上的错误声明照样报告，追加更正行不会消除它。
- **出错时的输出**：退出码为 2 时，输出 `fatal\t<原因>` 一行，不输出 `issue` 行。
- **持久化**：收尾时把输出写到 `.devflow/<slug>.reconcile-<YYYYMMDDTHHMMSSZ>-<6位随机hex>.txt`，不覆盖旧文件；出错时也一样写入（内容是那行 `fatal`）。哪个文件属于本次收尾，由 `close` 行的 evidence 明确引用，不按文件名猜"最新"。
- **出错时的处理**：对账出错不阻塞收尾，但收尾报告的 Attention 段必须写"对账失败：<原因>"；第三部分的页面把它显示为一条"对账失败"事项，不能显示成"0 个问题"。

**3. tick 收尾的步骤顺序**

1. 运行 `check.sh closeout`（截止时间已过不算问题）。然后在提交后的状态上重跑所有完成条件，记录真实输出。
2. **日志自查**：对照本会话的 transcript，检查日志的每一行是否对应真实动作、证据能否打开、有没有漏记的转折、撤回或守卫拦截。发现问题只追加更正行，不修改已有行。
3. **运行 `reconcile.sh` 并持久化**。这一步放在自查之后，这样对账结果和最终的日志是一致的。
4. 生成本次审查的时间戳和随机后缀，据此确定审查的作业文件和输出文件路径（见第 4 条）。然后写 `close` 行：decision 为"完成""部分完成 — …"或"受阻 — …"；evidence 写 `base <完整sha> head <完整sha> reconcile <文件> review <作业文件>`。
5. 写入作业文件 `{"state":"running", …}`，内容和 `review.sh` 启动时写的一样，确保页面从这一刻起就能显示"审查进行中"。然后删除运行标记，运行 `status.py --notify`，有事件就发一次通知。
6. **启动收尾后的审查**：用 Bash 的 `run_in_background` 运行 `review.sh`。这个调用立即返回，审查在后台继续。`review.sh` 发现作业文件已经存在、而且是 `running`，就沿用它，不重复写入。
7. 回复收尾报告，末尾附 Attention 段，内容是"审查进行中"加上对账的问题行，然后结束 loop。
8. 后台审查结束时，Claude Code 会唤醒本会话。会话读取作业文件，补发一段 Attention：先写 `reviewed by …`，再写审查意见，或者"审查失败/超时（原因）"。然后运行 `status.py --notify`，有新的审查标记就通知。如果会话已经关闭，这一步不会发生；但 `review.sh` 在写完终态后已经自己运行过一次 `status.py`（不带 `--notify`），所以磁盘上的页面已经显示审查的最终结果。审查标记对应的通知，会在下一次有人以 `--notify` 运行时补发。

**4. 收尾后的审查**

这时运行标记已经删除，守卫不再生效。审查只用 codex，没有回退。codex 失败或超时就记录为失败，由你决定要不要重跑。

- **新增 `review.sh <root> <slug> <base> <head> <timeout秒> <作业文件> <输出文件>`**，它负责：
  - **校验和隔离**：先用 `git rev-parse --verify` 把 base、head 解析成完整 SHA，任何一个解析失败就直接记为失败。然后在系统临时目录（`mktemp -d`）里准备一个证据目录：
    - `tree/`：`git archive <head> | tar -x` 导出的收尾时代码；
    - `diff.patch`：`git diff <base>..<head>` 的输出；
    - `meta.txt`：完整的 base 和 head、契约和日志的副本、transcript 路径列表。

    codex 以这个证据目录作为 `-C`，不进入活动仓库。所以即使收尾后有人改了工作区或 HEAD，审查读到的也只是收尾时的那个提交。这只是导出文件，不创建 worktree。审查结束后删除这个目录。
  - **收集 transcript**：从日志的各条 `start` 行里取出 `session <id>`，逐个查找 `~/.claude/projects/*/<id>.jsonl`，把找到的路径列表写进提示；找不到的列为"未核实"。
  - **作业文件** `.devflow/<slug>.review-<stamp>.json`：如果文件还不存在，启动时写入 `{"state":"running","base","head","started","timeout"}`；结束时原子改写为终态，`state` 取 `succeeded`、`failed`、`timeout` 之一，并补上 `finished`、`model`（取 codex 日志里的 `model:` 行）、`output`、`reason`。这个文件由 `review.sh` 自己写，不依赖会话是否存活。写完终态后，`review.sh` 再运行一次 `status.py <root>`（不带 `--notify`），让磁盘上的页面也变成最终状态。
  - **进程组和超时**：由一个小的 Perl 监督程序 `supervise.pl <超时秒> -- <argv…>` 统一负责，只用 macOS 自带的 Perl 5 和系统调用，不依赖 GNU 的 `timeout`、`setsid` 或 Bash 4 的 `wait -n`。它的步骤：
    1. `fork`，子进程里执行 `setpgrp(0,0)`，再 `exec` 审查命令；
    2. 父进程设置 `alarm(超时秒)`，然后 `waitpid` 等待子进程；
    3. alarm 触发时，先把"已超时"记在父进程的变量里，再对负的进程组号发 TERM，接着最多等 10 秒，期间用 `waitpid(WNOHANG)` 轮询；子进程还没退出就发 KILL，然后 `waitpid` 回收；
    4. 子进程正常退出后，父进程立即 `alarm(0)` 取消计时，再对负的进程组号发一次 TERM，清理可能残留的孙进程。这时进程组号仍然属于这个已结束的会话，组里没有进程时 `kill` 只是返回失败；
    5. 退出码：超时记录为真时返回 124，不管子进程实际以什么状态结束；否则返回子进程的退出码。

    因为计时就在父进程里，不存在单独的计时子进程，也就不会误杀被复用的进程号。
  - **审查命令**：默认是 `codex exec -s read-only --ephemeral --skip-git-repo-check -C <证据目录> -o <临时输出文件> "<参数行>"`，提示正文从标准输入读入，路径是 `review.sh` 根据自身位置解析出的 `../references/review.md` 绝对路径。
  - **测试接口**：设置了 `DEVFLOW_REVIEW_CMD`（一个可执行文件的路径）时，就用它代替 codex，按 argv 调用：`<可执行文件> <证据目录> <临时输出文件>`，提示正文同样从标准输入传入。
  - **成功的判定**：退出码为 0，而且临时文件非空。成功后在文件头部写入 `reviewed by <model>`、完整的 base 和 head，再用 `mv` 移到输出文件 `.devflow/<slug>.review-<stamp>.md`。
  - **退出码**：0 表示成功，124 表示超时，其他值表示失败。
- `<stamp>` 的格式是 `YYYYMMDDTHHMMSSZ-<6位随机hex>`，由 tick 在收尾第 4 步生成，所以不会覆盖历史文件。默认时限 20 分钟，契约里可以改短。
- **作业中断**：如果作业文件停在 `running`，而且距离 `started` 已经超过 `timeout` 加 5 分钟，页面就显示"审查已中断"，比如机器在审查途中休眠或重启的情况。
- **审查提示 `references/review.md`**：
  - 只看证据目录里的文件和列出的 transcript；
  - 回复第一行是总评，之后每条以 `- [<ts或sha>]` 开头，最多 30 行；
  - 没有问题就写 "No flags"；
  - 提示和参数行里都不能出现运行标记的文件名。
- 审查只标出问题，不动手修改，它的意见交给你处理。

**5. 停放的写法**：tick 规定写在 result 列，格式为 `parked: <原因>`。读取方两列都识别，兼容旧日志。

## 第三部分：进展页接入审查和对账结果

### 决定

- **新增两类待处理事项**：

  | 类型 | 来源 | 编号 |
  |---|---|---|
  | 审查标记 | 最后一条 `close` 行所引用的作业文件。状态为 `succeeded` 时，取其输出文件中以 `- [` 开头的行 | `<运行>/R-<stamp>-<n>`。审查文件不会被覆盖，所以编号稳定 |
  | 对账问题 | 最后一条 `close` 行所引用的对账文件中的 `issue` 行 | `<运行>/C-<12位hex>`。先把问题行规范化（`kind`、SHA、说明三段，连续空白合并为一个空格），再取 SHA-256 的前 12 位。编号和内容绑定，重新对账也不会漂移 |

- **对账失败**：被引用的对账文件里有 `fatal` 行的，生成一条事项 `<运行>/C-fatal`，显示"对账失败：<原因>"。
- **审查状态显示**：每个运行显示它的审查状态：进行中、成功、失败、超时、已中断，或者无审查（旧运行）。

- **答复动作**：这两类事项用"已查看"或"撤回"来处理。
- **通知**：沿用第一部分的规则，再加一条：出现新的审查标记时通知一次。

### 验收（第三部分）

- **C1**：合成样本中，同一个运行先后两次收尾（中间续跑过一次），两条 `close` 行各引用一份对账文件和一份作业文件。两份对账文件在同一秒生成，第二份删掉一条问题、新增一条问题，另外还有一条问题的 kind 相同、说明不同。检查：
  - 页面只采用最后一条 `close` 行引用的那两个文件；
  - 编号符合规则，kind 相同、说明不同的两条问题编号不同；
  - 对其中一条答复"已查看"后，它在第二份对账文件里仍然对应原来那条；
  - 删掉的那条从队列里消失，新增的那条进入队列；
  - 以 `--notify` 运行时，新增的审查标记触发一次事件；
  - 作业文件为 `running` 且已超过时限加 5 分钟的 → 显示"审查已中断"。
- **C2**：A5 的端到端运行结束后，页面上能看到审查标记和对账问题，作答后能关闭。

## 风险

- 登记表依赖武装和续跑时写入。绕过 `/devflow-autorun` 的运行会显示为"未挂接"，需要人来挂接。
- 页面只在 tick 运行或手动运行脚本时刷新数据。没有在跑的项目，页面停在最后一次生成的时间（页面上会显示这个时间）。
- PushNotification 只有连上 Remote Control 才会推送到手机。
- 审查只依赖本机的 codex 和它的模型代理，速度波动大。超时只影响审查本身，不影响收尾。codex 不可用时，这次运行就没有跨模型审查，页面上显示失败的原因。会话关闭后不会再主动补发 Attention 和通知，但作业文件和页面上的状态照样有效。
- 花费命令由用户在武装时确认，`status.py` 只限制执行时间，不对命令做沙箱隔离。

## 附录 A：用户已确认的决定

- 进展页本地生成；写回方式为"一句话 + `log.sh` 命令"，写入 `roadmap.tsv`；派发回执和 Codex 支持不在范围内；花费由契约可选的命令提供。
- 删掉 HEAD 检查，接受丢失即时保护的代价。
- "武装步骤被跳过"不在本方案范围内。
- 先做进展页，后做日志修订；跨模型审查移到收尾之后，不阻塞收尾。
- 去掉审查的 Claude 回退：codex 失败或超时就记录为失败，由用户决定要不要重跑。
