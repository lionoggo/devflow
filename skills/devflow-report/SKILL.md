# Git 工作进展报告

根据 Git 记录归纳用户在一个时间段内的主要事项与可验证进展。默认只生成事项清单，不额外生成定长重点总结。

## 输入与范围

确认或从用户请求中解析以下信息：

- Git 仓库路径和起止时间。用户未指定时间时，默认使用当前本地时间为截止点的最近 7 天，并在输出中写明实际起止时间；用户使用“本周”等有多种解释的表达时先询问，不擅自解释为自然周或最近 7 天。
- 使用仓库当前配置的 `git config user.email` 作为唯一归属条件。无法读取时，说明原因并请用户提供邮箱；不要猜测姓名、使用全局 Git 配置或混入其他作者的提交。
- 默认只检查当前 `HEAD` 可达历史。用户明确要求跨分支汇总时才使用 `--all`，并按 commit hash 去重。
- 默认不包含工作区修改。用户明确要求“包含未提交修改”时，才将其列为单独的“未提交进展”，不能写作已完成或已交付。
- 用户指定“按创作引擎/素材管线/Studio”等主要事项分类时，将这些名称视为输出分类，而不是仅供参考的关键词。

所有 Git 操作保持只读；不要创建提交、切换分支、暂存、清理工作区或写入周报文件，除非用户另行要求。

## 收集证据

先读取邮箱、仓库状态与该时间范围内匹配 author 的提交。优先使用结构化 Git 输出，例如：

```bash
git config user.email
git log HEAD --author="$AUTHOR_EMAIL" --since="$START" --until="$END" \
  --format='%H%x09%ad%x09%s' --date=short
git show --format= --name-status <commit>
git show --stat --format='%H%n%s%n%b' <commit>
```

仅在文件名、提交说明和统计不足以判断事项时，再读取与该事项直接有关的 diff 或文档正文。对方案类变更，重点辨别其状态：新增/修订方案、调研结论、实现完成、验证完成或待推进；不要把“设计了方案”改写成“上线了功能”。

同时收集该时间段内由当前 author 提交的 Markdown、设计方案、规格和指南类文档。只有文档内容与某个事项直接对应时，才将其作为“相关文档”候选；不要仅因目录相邻或文件名相似就建立关联。必要时可在相关模块的 `docs/` 中查找当前仍有效的配套文档，但不要对整个仓库做无边界扫描。

需要包含未提交内容时，分别检查暂存区、未暂存区和未跟踪文件。只把有明确差异或可读取内容的文件作为证据，并在输出中标明状态：

```bash
git status --short
git diff --cached --stat
git diff --stat
```

未跟踪的方案文档可在用户要求包含未提交内容时纳入，但仅描述文档中明确写出的内容；不要把文件名当作已完成的证据。

## 归纳规则

- 按共同目标、相邻目录、相关提交主题和方案文档关联，把多个提交归并为少量有业务含义的事项；不要机械地“一条 commit 一项”。
- 用户未指定分类时使用上述自动聚类。用户指定分类时，优先保持其分类名称、顺序和粒度，并把每项进展归入主要成果所属的一个分类，避免同一成果在多个分类重复出现。
- 用户使用“等”等开放表达时，可为无法合理归入给定分类的重要工作补充最少数量的新分类；用户给出封闭分类或明确说“只按这些分类”时，不擅自增加分类。给定分类没有可验证进展时默认省略，用户要求保留完整模板时再输出空项说明。
- 事项之间证据不足以合并时，宁可拆分；只有同一主题的实施、测试和文档更新能形成清晰因果链时才合并为主项和子项。
- 每项只描述记录能支持的事实：改了什么、完成了何种验证、当前处于什么阶段。提交标题含糊、证据不足时，用保守表述或列出待确认点。
- 忽略纯格式化、合并提交、版本同步等没有独立业务价值的噪声，除非它们是该时间段的主要工作或用户要求完整流水。
- 代码、测试与方案文档属于同一目标时，在同一事项下分别说明；不要因文档和实现各有一条记录而重复计数成果。
- 主事项标题优先表达工作目标或成果领域，首句说明进展和产生的结果；具体模块名、内部机制与测试细节放在子项。除非是沟通所必需，不在主事项中堆叠代码符号和中英文术语。
- 结论应在分析过程中保持可追溯，但默认正文不展示 commit hash、文件路径、文档名或“证据”标记。只有用户明确要求来源、提交明细或证据时，才在正文之后增加独立的 `证据附录`，不要把证据内联到事项或子项中。
- 相关方案或规格文档不属于证据附录。若存在与事项直接对应且当前有效的文档，在该事项末尾增加一个 `相关文档` 子项，以 Markdown 链接展示文档标题；没有对应文档时不输出空的文档项。
- 链接优先使用文档已有的 HTTP(S) 地址或已确认可访问的仓库 Web 地址。无法可靠生成远端地址时，在本地对话中使用该文件的绝对路径链接；不要猜测代码托管平台的 URL 规则，也不要输出不可点击的伪链接。未提交文档只有在用户要求包含未提交内容时才可链接，并标明“草稿”。

## 默认输出

直接输出中文 Markdown，使用以下形状；没有实际子项时不要强加子列表：

```markdown
- 事项 A：事项介绍，以及已验证的进展或成果。
  - 子项 A：具体实现、方案或验证结果。
  - 子项 B：后续状态或关联变更。
  - 相关文档：[方案名称](文档链接)
- 事项 B：事项介绍/进展或成果。
```

正文应能直接粘贴到周报中。不要默认输出 author 邮箱、commit 列表、文件路径或证据说明；时间范围可在事项列表前用一行简短文字标明。

用户明确要求证据时，使用与正文分离的附录：

```markdown
## 证据附录

- 事项 A：`abc1234`、`path/to/file`
- 事项 B：`def5678`
```

若没有匹配提交，明确说明“该时间范围内未找到当前 author 邮箱的已提交变更”，并可在用户要求时另列未提交进展；不要凭工作区文件推测历史工作。

## 定长重点总结（仅在用户要求时）

先给出默认事项清单，再增加 `## 重点总结`。总结覆盖最重要的 2–4 个事项、结果和下一步，避免逐项复述。

- 用户给出字数时，中文按字符近似控制在不超过该上限；标题和 Markdown 标记不计入正文。
- 用户只说“简短总结”而未给字数时，先询问字数或明确采用的长度。
- 未提交内容如被纳入，只能表述为“正在推进/已形成草稿”，不可称为“已提交/已完成”。
